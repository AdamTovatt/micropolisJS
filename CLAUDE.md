# CLAUDE.md

## Project Overview

A continuation of [micropolisJS](https://github.com/graememcc/micropolisJS), Graeme McCutcheon's hand-written JavaScript/HTML5 port of Micropolis — the GPL release of the original 1989 SimCity. The game runs entirely in the browser: a 120×100 tile city, simulated in the browser, drawn on a canvas, saved to `localStorage`.

This repository is Adam's private continuation. The aim is to grow it from a faithful single-player port into the foundation of a multiplayer city builder with a richer simulated world. The **Direction** section below is the source of truth for where the code is heading.

| Component   | Technology                                                                         |
|-------------|------------------------------------------------------------------------------------|
| Language    | TypeScript in the browser, and JavaScript (ES5-style prototypes) in the legacy simulation modules; C# on .NET 10 for the server |
| Bundler     | webpack 5 + ts-loader, entry `src/micropolis.ts`, output `dist/`                   |
| UI          | plain DOM windows in `index.html`, on `windowBase.ts`; the map on a `<canvas>`     |
| Server      | ASP.NET Core on .NET 10, `server/Micropolis.slnx`; EasyReasy.Auth for tokens       |
| Tests       | Jest + ts-jest, `test/*.ts`; MSTest, one test project per C# project               |
| Persistence | JSON in `localStorage` (`src/storage.ts`, the save format in `src/savedGame.ts`)  |

## Direction

Work that pulls against this needs Adam's go before it starts.

1. **A deterministic, headless simulation.** The simulation runs without a DOM (in Node, and in C# after the port), advances by explicit steps rather than wall-clock time, and produces the same city from the same seed and the same sequence of player commands. Everything below builds on this.
2. **Server-authoritative multiplayer on a C# server.** The server owns the simulation. Browsers send commands ("road from A to B", "set tax to 9%") and render the state the server sends back. A player edit is a command the simulation applies, never a direct write to the map from UI code. Every player has the same powers: any player can issue any command, and the simulation never branches on who sent one.
3. **The TypeScript simulation is the reference until the C# port replaces it.** Everything that changes or computes city state moves to C#: the simulation, sprite behaviour, map generation and the random stream, applying and validating commands, save and load. The port is correct when it reproduces the TypeScript simulation's state hash from the same seed, starting state and command log. Once it does, the TypeScript simulation is deleted and the C# code is the only home of the game rules. Command logs are both the end-to-end suite and the conformance suite: replayed headless and in the browser while the TypeScript simulation exists, and on the server after. Anything in the simulation that another language can't reproduce bit for bit is a defect.
4. **The browser is the client.** It draws tiles and sprites, animates tiles, captures input (tool choice, the hover box, turning drags into tile paths) and shows the windows. It changes city state only by sending commands. Map overlays and query-tool data come from the server on request.
5. **A modernised client.** Client code is TypeScript and works on the DOM directly, without jQuery. Simulation modules are not converted: the C# port retires them.
6. **Gameplay improvements on top of the original rules**, such as ships that sail to the seaport instead of wandering the channel at random. They are built in the C# simulation after the port, so each rule is written once.
7. **Longer horizon, not planned in detail:** a richer generated world (climate and weather driven by parameters, natural resources, choosing where to found a city), several cities linked by road and rail, individually simulated residents, and LLM-driven notable residents whose behaviour may later be distilled into a small model of our own.

### Open decisions

Ask before writing code that settles an open decision; record the decision under Decided when it is made.

#### Decided

- **Multiplayer shape.** One shared city, run in real time by several mayors, each with every power a single player has: any player can build, bulldoze, set taxes and the budget, trigger disasters, pause and change the speed. Pause and speed are commands like any other and apply to everyone. The simulation never branches on who sent a command.

## Commands

```bash
npm install
(cd server/Micropolis.Server && dotnet run)   # server and client together: open http://localhost:5180
npm run dev              # webpack-dev-server on http://localhost:44903, the client alone
npm run build            # production bundle into dist/
npm test                 # Jest
npx jest test/tile.ts    # one test file
npm run lint             # ESLint over src/, test/, headless/, e2e/ and the build config
npm run simulate -- --fixture town --steps 3000   # headless run: prints the state hash, year, population, funds
npm run simulate -- --log session.json            # replay a command log and check its checkpoints
npm run fixtures         # export each fixture's log to headless/fixtures/export/ (ignored by git)
npm run e2e              # the end-to-end playthrough in headless Chromium; report in e2e-report/
npm run e2e:golden       # run the playthrough to rewrite its checkpoints and log, e2e/goldenPlaythrough.json, if it passes
npm run conformance      # regenerate the conformance files the TypeScript reference computes (conformance/README.md)
npm run benchmark        # time the C# simulation on the fixtures and rewrite docs/benchmarks.md
dotnet build server/Micropolis.slnx   # the C# solution
dotnet test server/Micropolis.slnx    # MSTest
```

`dotnet run` in `server/Micropolis.Server` is the dev command, and `remote-claude.json` binds the dev-server button to it. The server listens on :5180, and SpaProxy starts `npm run dev` unless something already answers on :44903, then sends the browser there; whatever answers on :44903 is the client it uses. webpack-dev-server proxies `/api` and `/ws/city` to the server, and accepts any Host header, so a reverse proxy can front it under another name. The server will not start without two settings, which development takes from `Properties/launchSettings.json`: `JWT_SECRET`, at least 32 bytes, and `TRUSTED_PROXIES`, the addresses of the reverse proxies in front of the server, separated by commas, or `none`. Behind a proxy it does not trust, the server sees every player at the proxy's address, and they share one sign-in rate limit. `dotnet publish` runs `npm ci` in the repository root, which deletes and reinstalls `node_modules`, then `npm run build`, which overwrites `dist/`, and copies `dist/` into the published `wwwroot`, which the server serves.

The headless runner takes `--seed <n>` (a generated map) or `--fixture <name>`, `--reseed <n>` to replace a fixture's stream, `--speed slow|medium|fast` to override the saved speed, and `--steps <n>`; or `--log <file>` alone, a command log (`docs/command-log.md`), such as one the debug window downloads.

Node 24 or later (`engines` in `package.json`), and the .NET 10 SDK for `server/`. CI (`.github/workflows/ci.yml`) runs on every push and pull request: one job runs `npm ci`, then build, test and lint, on Node 24, and checks that the files `npm run conformance` writes are committed as it writes them; another checks `conformance/random.json` against the program that writes it, then builds and tests the C# solution, which reads the conformance files as committed, and runs the benchmark for a few steps, checking only that it writes its table. After the first, a third runs the end-to-end suite, uploading its report whether it passed or not, and the traces of the tests that failed when one did.

`npm run e2e` serves a production build with webpack on port 8181 (`E2E_PORT` moves it) and never reuses a server already there. The page's requests to the game server's API are refused, so the game plays single-player even while a server answers on :5180, such as this checkout's dev server. A test that fails leaves its trace in `e2e-results/`, which `npx playwright show-trace` opens. Playwright's Chromium comes from `npx playwright install chromium`.

Tests are TypeScript and can import the legacy JavaScript modules: ts-jest compiles both for Jest, and Playwright compiles `e2e/` without checking types. The build's ts-loader type-checks every TypeScript file in the repository, `test/` and `e2e/` included, so `npm run build` fails on a type error anywhere. The game's Settings window and the footers of the about and name-license pages show the build ID, `git rev-parse --short=12 HEAD`, or `unknown` outside a git checkout.

Open the game with `?debug=1` in the URL for debug mode (`ClientConfig.debug` in `clientConfig.ts`, which each city source passes on to the simulation's `Config.debug` in `config.js`): an undefined event name in the simulation throws instead of warning, the FPS counter shows, the query window shows the raw values of the simulation's report on the tile in its debug rows, the splash screen offers "Load save file" for a save's JSON (such as an end-to-end checkpoint's), and `window.micropolisTestHook` (`testHook.ts`) is installed. `?seed=<n>` starts the splash screen on that seed's map instead of a random one, with or without debug mode; a seed that isn't a uint32 raises an alert and the map is picked at random. Both are read by `urlOptions.ts`.

### End-to-end suite

`e2e/playthrough.spec.ts` plays one city from a fixed seed through an ordered list of stages (`e2e/stages.ts`), the way a player would: real mouse and keyboard on the canvas and the windows, through `e2e/player.ts`. Adding a stage is the normal way to cover a new feature; a stage builds only on the site `SITE` names, which it may widen, and which the first stage checks is clear land on the seed's map, or where it chooses from the city's state. The fire stage does the latter: wherever the random stream lands the fire, it reads the burning tile from the save and builds a fire station whose cover reaches it at the strongest, with a road and a power line to the grid (`e2e/stationSite.ts`), scrolling the view with the arrow keys to reach them. So a rule change that moves the stream moves only the goldens, unless it lands the fire where no such site is near, and then the stage fails naming the fire. The test hook holds the city source's step driver for the whole run, through the source's asynchronous driver channel (`CityDriver` in `citySource.ts`), which is not the game's pause. While it is held, the game's tick still reads the mouse and keyboard, but sends no tool paths, and the source applies no commands: the runner does both after each action with the hook's `applyInput()`, so each action becomes the same commands on every run. The runner moves the city on only through the hook's `advance(n)`, which sends the input first, then has the source apply the commands and take the steps, and fails when city time falls short of the steps taken, as `cityTimeModel.ts` models it. The source sends the state those steps changed before the advance resolves. So every input lands between the same two steps on every run. Each stage ends in a checkpoint: its step count, the commands applied so far, its state hash, a screenshot and the save, which the report (`e2e-report/index.html`) shows in stage order under the build ID and seed. The runner hashes the simulation's part of the save in Node with `stateHash.ts`, and checks it against the stage's golden checkpoint in `e2e/goldenPlaythrough.json` (`e2e/goldenPlaythrough.ts`); a checkpoint whose hash, step or commands differ fails the run, which carries on so the report is complete, and the failure, at the top of the report too, names the first stage that diverged. A stage with no golden checkpoint fails the same way, so a new stage is pinned with `npm run e2e:golden`, which writes the file only from a run that passed: every stage, its command log and the browser's own driver. The screenshots are for looking at, never compared by the suite. The page's date is fixed for the run, and the client's tile animation and blink take their frame from it; the runner scrolls the view to the same origin on every run, whatever the timing of its key presses; and nothing that closes on wall time is left closing at a screenshot: each dismisses the notification bar through the test hook first, and no stage ends while the disaster view counts down to closing. So a stage's screenshot is the same on every run and two builds' screenshots can be compared pixel for pixel. Each reload ends a session, as the end of the stages does: the runner downloads each session's command log from the debug window and joins them in order into the run's log from the seed (`joinSessions` in `commandLog.ts`), which needs no entry for a load, since a load is transparent. The run's log must be the golden file's, and `test/playthroughReplay.ts` replays that log headless to every checkpoint, the game's own and each stage's, as `docs/command-log.md` describes. After the stages the runner releases the driver and waits on city time; a run whose step count depends on wall time has no reproducible state, so the report shows a screenshot of it and no save. The runner finds tiles on screen from the view's origin, not through the game's own pointer-to-tile mapping, which is under test.

`e2e/saveFile.spec.ts` tests debug mode's "Load save file". `e2e/splashScreen.spec.ts` tests how the page starts: waiting for the tile image, and reporting one that fails to load, waiting while the screen is too small to play, refusing a `?seed` that isn't a uint32, and the start form, where a city needs a name outside debug mode and one left unnamed in debug mode is MyTown.

## Architecture

### Layers

- **Simulation** — DOM-free. `simulation.js` orchestrates; the subsystems are `mapScanner.js`, `residential.js`, `commercial.js`, `industrial.js`, `road.js`, `transport.js`, `powerManager.js`, `traffic.js`, `stadia.js`, `miscTiles.js`, `emergencyServices.js`, `valves.js` (residential/commercial/industrial demand), `census.js`, `budget.js` (funding services through `serviceFunding.ts`, with `budgetRecord.ts`, the budget record the budget window shows), `evaluation.js` (with `evaluationRecord.ts`, the evaluation record the evaluation window shows), `settingsRecord.ts` (the settings record the settings window shows), `disasterManager.js`, `blockMapUtils.js`, `cityStatus.ts` (the advisor conditions and the city status record). `commands.ts` and `queries.ts` are simulation code too: how the commands are validated, and how the queries are validated and answered, on the checks in `validation.ts`, which the C# port reproduces.
- **City source** — the client reaches the city only through a `CitySource` (`citySource.ts`): it sends commands and queries, and the source delivers the state messages the city sends back (`protocol.ts`, `protocol/README.md`). The page imports no simulation module, not even for a type, but the vocabulary the two share, which `test/clientImports.ts` enforces: `protocol.ts`, the messages themselves; `messages.ts`, the names of the news subjects and advisor conditions those messages carry; `tileValues.ts`, the tile ids, by which the client draws and animates tiles; and `tileFlags.ts`, the flag bits of a tile's raw value, which the client masks and reads. A module joins the vocabulary only with its reason written here. `cityState.ts` is the client's copy of the city, built from those messages alone: the map, from the full map the city sends when it starts and the tile changes after it, and the latest message of each other type since the city started. The simulation's side of a source in the browser is `cityHost.ts`: it owns the `Simulation`, the command queue, the session's command recorder, and the step driver, and steps the city itself at the speed it was set to, on a loop of its own that runs from the first city's start. While the city isn't stepping (paused, unseen or held) the loop waits, and the next command, the player seeing the city again or the runner's release wakes it. After each turn of its loop that applied commands or took steps, and each call of the end-to-end runner's driver that applies commands or takes steps, it sends one batch of state messages: the tiles that changed, found by diffing the map against its own copy; the sprites, the date, the population and the records that differ from those it sent last; the latest `status` and `demand` the simulation published since the last batch; and the events since then in the order they came (news, command results, budget reviews due, and each recomputed overlay layer once). The page tells the source whether the player can see the city, which isn't a command: in a hidden tab or under the screen-too-small overlay the source stops stepping. The page plays through the Worker source (`workerCitySource.ts`): the host runs in a Web Worker, off the page's thread, which `micropolis.ts` starts from `cityWorker.ts`. The worker serves the host (`cityWorkerHost.ts`) over the messages `cityWorkerMessages.ts` defines, starting with whether the page is in debug mode, and answers each call after the state messages it caused, so the page has the state before the call resolves. What goes wrong in the worker outside a call, a promise rejected with no one to catch it included, is raised in the page. `test/workerImports.ts` checks the worker's TypeScript modules against the Web Worker library, which has no `window` or `document`. `pageCitySource.ts` is the in-page source, which runs the host on the client's own thread: the client's tests run against it. Both sources pass the same contract tests (`test/citySource.ts`). The bundle is built from ES modules, which `new Worker(new URL(..., import.meta.url))` needs, by an override of ts-loader's module settings in `webpack.config.js`; `tsconfig.json` stays on CommonJS for ts-jest. `stepDriver.ts` turns real time into steps at a fixed 60 per second. It catches up after a slow frame, up to a second's worth of steps at a time, and drops the rest of a longer gap. It owes nothing while the city is not stepping: paused, while the player can't see it, or while the end-to-end runner holds it. Map previews are a `mapPreview` query, which a source answers before any city has started; a save's text goes to the source and back unread by the page, which only stores it (`storage.ts`).
- **Game and UI** — `game.ts` shows a city a source has started: the canvas and the windows (`*Window.ts`), drawn from the client's copy of the city. It runs two loops: `tick` (`setTimeout(0)`: the mouse and keyboard, then the tool paths drawn since the last tick, which it leaves to the end-to-end runner while that holds the step driver) and `animate` (`requestAnimationFrame`: painting the latest state). It tells the source whether the player can see the city as the tab's visibility changes or a resize shows or hides the screen-too-small overlay. `windowManager.ts` shows the windows one at a time, each built on the plain-DOM base in `windowBase.ts` by extending `ClosableWindow`. A window that shows city figures opens on a plain record the simulation produces or on a query's answer, never on simulation objects, and turns any codes in it into text through `text.ts`. The budget window opens on the budget record, which places its sliders, and shows every figure from the answer to a `budgetForecast` query, which it asks through a `QuerySource` when it opens, on Reset and each time a slider moves. The settings window opens on the settings record beside the settings the client keeps, which `game.ts` builds. A window closes with the player's choices as plain data, and imports no simulation module. A window showing holds the keyboard and mouse; no window holds the city. The year-end budget never waits for the player (see `Budget.doBudgetNow`): with auto-budget off, or when auto-budget couldn't cover the services, the budget window opens as a review once no other window shows, and the player's changes there are a `setBudget` command. `windowCommands.ts` turns the windows' choices into commands. Milestones are good-news notifications, not windows. `news.ts` decides where a message the simulation sends goes: to the notification bar, and for a disaster or a crash, the place it happened to the monster TV; neutral news that arrives while a disaster is recent is not shown. `speedControl.ts` sends the speed the player sets with Pause, Play and Settings as `setSpeed` commands, and shows the pause button from the speed in the settings record, the only record of whether the game is paused. The auto-bulldoze setting is the player's preference (`autoBulldozePreference.ts`), kept under its own `localStorage` key and sent with each tool command, never saved with the city.
- **Headless** — `headless/` runs the simulation in Node through `tsx`, without a browser: `runner.ts` starts a city from a seed or a fixture and steps it, failing rather than stalling silently (`cityTimeModel.ts` takes the steps and checks city time kept up, for it and the end-to-end test hook alike), and replays command logs; `run.ts` is its command line, which `cli.ts` prints. A fixture is a command log in `headless/fixtures/`, whose checkpoints are its golden hashes. Its script either lays out its tool commands, or takes the city another fixture's commands build, writes onto it what no command places, and starts the log from that city's save. The runner and the TypeScript tests build a fixture by replaying its commands each time they use it, then load its saved state. The copies of its state in `conformance/saves/`, and of its log in `conformance/logs/`, are for the C# tests, and the saves for the benchmark too. The state hash (`stateHash.ts`, specified in `docs/state-hash.md`) is SHA-256 over the canonical text of the saved state.
- **Rendering** — `gameCanvas.ts` draws 16×16 tiles from `images/tiles.png` through `tileSet.ts`, and sprites from `images/sprites.png`. `animationManager.ts` animates tiles from their value and the client's clock, and never writes the map: an explosion holds its last frame until the simulation's scan turns the tile to rubble. `monsterTV.ts` is the small disaster-follow view, which follows a monster or tornado by its type through the sprites messages, and `splashCanvas.ts` the map preview on the splash screen. A map overlay tints each tile as the canvas paints it, under the sprites: `overlayRenderer.ts` draws one layer's colour ramp and legend from the simulation's answer to an overlay query alone, never from simulation objects, and has the canvas repaint every cell when the overlay changes or the view scrolls under it; `overlayPicker.ts` asks for the layer the player picks, and again each time the simulation announces it recomputed.
- **Server** — `server/` is a .NET 10 solution, `Micropolis.slnx`, with a test project per project. `Micropolis.Rules` holds the game rules and the server's half of the protocol, and has no ASP.NET dependency, so a test or a tool can run them without a host. `Micropolis.Benchmarks` is such a tool, a console app: for each fixture's save in `conformance/saves/` but those its `BenchmarkCases.NotRun` names with the reason, and a new city at each running speed, it times the simulation's steps and writes a Markdown table of steps per second and time per step, with the machine, its load average, the runtime and the commit. Given the state-message bytes per step of each case, it adds them to the table, after checking that the city they were measured on ends at the state hash its own timed city does. `npm run benchmark` builds it in Release, measures each case's bytes on the TypeScript city host (`headless/messageBytes.ts`), and has it write `docs/benchmarks.md` with them; the report says what the bytes were measured on. `server/Micropolis.Benchmarks/examples/` holds an example of each file the two halves hand each other, which both test suites read. `Micropolis.Server` is the ASP.NET Core host. `POST /api/session` signs a player in with a display name only, a few times a minute per client address: the token's subject is a new player id, the name is the only claim the server adds, and it carries no roles, because no player can be denied anything. `GET /api/session` answers who a token belongs to, or 401, which is also how the browser finds out that a server answers. `/ws/city` is one plain WebSocket of JSON messages, where `PlayerPresence` lists who is online and each `CityConnection` is the one writer to its socket. The server closes a connection when its token expires.
- **Server connection (client)** — `cityClient.ts` signs in and holds the city's WebSocket, with no DOM, so its tests drive it through a fake browser; `browserCityEnvironment.ts` gives it the browser's fetch, WebSocket, storage and locks. With no server answering, the game starts single-player. Once online, it reconnects after a drop with growing delays, and signs in again under the stored name when the server rejects its token, one tab at a time, so tabs sharing a session stay one player. `signInForm.ts` asks for a name before the splash screen when a server answers and no session is stored, or the server refuses the stored name, and `onlineList.ts` shows who is online, or "Offline", over the top of the map.
- **Protocol** — `src/protocol.ts` and `server/Micropolis.Rules/Protocol.cs` define the bodies of `/api/session`, the WebSocket's messages and the commands by hand. `src/protocol.ts` also defines the queries with their answers, and the records the simulation produces for the windows to show. `protocol/README.md` specifies the wire format, and the examples and reader cases under `protocol/` pin the sides together: each test suite reads in place the examples of what its side reads or writes.
- **Conformance data** — `conformance/` holds what the C# implementation of the game rules tests against, and what computes it: the random stream's vectors, from a C reference that the TypeScript tests read too, and files the TypeScript reference writes. The C# tests read them in place. `conformance/README.md` describes each file.

### The simulation cycle

`Simulation.step()` is one loop, as `simLoop` in the original: `_simFrame()` gates on the game speed, then every sprite moves. The gate is the saved `_speedCycle` counter, which lets a phase through on every 5th step at slow speed, every 3rd at medium and every step at fast. A paused simulation's step does nothing. The step count, never wall time, advances the city. Each step that passes the gate runs `simulate()`, which advances one phase of a 16-phase cycle:

| Phase | Work |
|-------|------|
| 0     | advance `_cityTime` and `_simCycle`, set the demand valves, clear the census |
| 1–8   | scan one eighth of the map's columns each, calling the tile handlers |
| 9     | census, tax collection and city evaluation at their frequencies |
| 10    | decay the rate-of-growth and traffic maps, send advisor messages |
| 11–15 | power scan; pollution, terrain and land value; crime; population density; fire coverage and disasters, then publish the city status record |

How often phases 11–15 run depends on the game speed (`speedPowerScan` and its siblings in `simulation.js`), so speed changes simulation results. It is simulation state, not a display setting.

### Tile handlers

Subsystems register handlers with `mapScanner.addAction(tileValueOrPredicate, handler)` from `registerHandlers`, all called in `Simulation.init`. During phases 1–8 the scanner calls the handler for every matching tile with `(map, x, y, simData)`; `simData` (from `_constructSimData`) carries the census, budget, block maps, the random stream, the sprite manager and the other managers.

### State

- `gameMap.js` holds the tile grid. `tile.ts` is a tile's value plus flags (`tileFlags.ts`: powered, conductive, burnable, bulldozable, zone centre…). `tileValues.ts` names every tile id (`RIVER`, `CHANNEL`, `PORT`…).
- `simulation.blockMaps` holds coarse overlays at block sizes 2, 4 or 8 (`blockMap.ts`): land value, pollution, crime, traffic density, population density, police and fire coverage, rate of growth. Each map's comment in the `Simulation` constructor states its range.
- `simulation.random` is the simulation's random stream (`random.ts`), seeded from the game seed. The map generator draws from the same seed's map stream, so one seed reproduces map and city. The `random.ts` header specifies the stream, which the C# port (`RandomStream` in `server/Micropolis.Rules`) reproduces bit for bit. `conformance/random.json` holds reference vectors computed by the reference C implementation, and the tests of both read it in place.
- A stateful component's `save(saveData)` and `load(saveData)` write and read its fields under its own key of the save. What the scans derive is saved under `scannedState` instead, through `saveScan` and `loadScan`: the census has both pairs, and the power manager, which holds only scan results, has only the scan pair. `test/savedFields.ts` fails on a field a component holds but neither saves nor explains. A save holds the complete simulation state, the stream's included, so a loaded city continues exactly as it would have without the save; `docs/state-hash.md` lists every key, and a field the simulation adds is saved and listed there too. The `Simulation` constructor starts a new city from a seed, and `Simulation.fromSave` builds one from a save. `Simulation.load` restores a save over a city of the same map size, and nothing of the city it replaces survives. It restores without scanning, except for a browser save that `transitionOldSave` migrated from a version without the scanned state: that save's scanned state is `null`, so loading derives it by scanning from a new city's scanned state, then restores the rest of the save over whatever the scan changed. `savedGame.ts` writes the combined object, versions it (`SaveFormat.CURRENT_VERSION`) and migrates old saves (`transitionOldSave`), on the simulation's side of the city source; `storage.ts` keeps the text in the page. The version is one past the last of the migration steps in `UPGRADES`, each of which upgrades a save from its place in the list, so a step only ever goes at the end. A change to saved state appends a migration step, which bumps the version, updates the golden hashes, regenerates the conformance files (`npm run conformance`) and changes the C# save model in `server/Micropolis.Rules` to read it, in the same commit. The same commit appends the same step to `Upgrades` in `SavedGame.cs`, which migrates saves in C#, and adds a sample save of the new version, written by the game of that commit, to `conformance/saveVersions/`.

### Events

`eventEmitter.js` decorates a simulation constructor or object with `addEventListener`, `removeEventListener` and `_emitEvent`. Event names live in `messages.ts`, each a string no other message shares, since listeners and the unit snapshots tell events apart by the string; `test/messages.ts` fails on two that share one. Subsystems emit, `Simulation` re-emits upward, and the city host turns what it hears into state messages for the client: the simulation never calls UI code. The client's windows and input announce what the player does through their own base, `Emitter` in `emitter.ts`.

A condition that holds over time (power load against capacity, a demand cap, an advisor warning) is state, published each cycle in the `CITY_STATUS_UPDATED` record, which reaches the client as a `status` message that `statusPanel.ts` renders. A `FRONT_END_MESSAGE` notification announces a condition or a one-off event and then times out; the record is what shows a condition for as long as it holds. The record is built each cycle and not saved, but its sources are: the power figures from the last power scan, and the cap flags from the valves.

### Sprites

`spriteManager.js` and the `*Sprite.js` files: train, ship, plane, helicopter, monster, tornado and explosion. Sprites move once per simulation step (`Simulation.step` → `spriteManager.moveObjects`), at the same rate whatever the game speed, and draw from the simulation's stream, so their behaviour, including the map damage a crash, monster or tornado causes, is part of the deterministic simulation.

### Commands

Every change a player makes to the city is a command: plain JSON, defined in `protocol.ts` as part of the multiplayer protocol. UI code never writes to the map, the budget or the managers. `Simulation.applyCommands` validates each command (`commandRejection`) and applies it, separately from `step()`. A rejected command changes nothing. Each command's result, with the player who sent it, its outcome and the reason for a rejection, is emitted as `COMMAND_RESULT`; the simulation never branches on the player. `commandQueue.ts` drives a simulation as the city host does and the server will: commands queue as they arrive and apply in arrival order whenever `applyCommands` is called, every turn of the host's loop whether or not the city is stepping, and each is stamped with the index of the step it precedes. The queue hands each stamped command, and each step before it is taken, to a recorder: `commandLog.ts` records the session's command log (`docs/command-log.md`), with a checkpoint of the state hash every 3,600 steps, which the debug window downloads and the headless runner replays. The UI turns clicks and drags into tile paths: `dragPath.ts` gathers the tiles the tool reaches, filling in those a fast mouse skips, and each tick sends a drag's new tiles as one tool command.

A query asks the simulation about the city and changes nothing: plain JSON, defined in `protocol.ts` beside the commands. `Simulation.answerQuery` validates it (`queryRejection` in `queries.ts`) and answers at once, with a copy of what it reads; it never draws from the stream and is never logged. An `overlay` query names a layer, one of the block maps the player can see or the power grid, and is answered with the layer's block size, range and values. The simulation emits `OVERLAY_UPDATED` with a layer's name once the phase that recomputes it has run (`LAYER_PHASES`), which reaches the client as an `overlayUpdated` message, and an overlay showing that layer asks again. A `tileReport` query names a tile, and is answered with the tile's raw values and its category, the table of the original's `doZoneStatus`; the client sorts the values into the bands the query window shows. A `budgetForecast` query names the funding of some services, and is answered with the budget record and what the year end would cost and leave at that funding, as `Budget.forecast` works it out. A `mapPreview` query names a game seed, and is answered with the map a new city on it starts on, before any city has started too.

### Tools

`*Tool.js` on top of `baseTool.js`; `cityTools.ts` builds the tools that change the city, with their costs, which the simulation applies tool commands with. A tool command applies its tool at each tile of its path in order, as one click each: the tool stages its edits in a `WorldEffects` (`worldEffects.js`), drawing from the stream as it goes, checks the funds, then writes the staged tiles to the map and charges the budget. The query tool (`queryTool.ts`) belongs to the UI: it sends a `tileReport` query for the tile clicked, and the query window shows the answer. It asks, as the overlay picker does, through a `QuerySource` (`querySource.ts`), which the city source is.

## Rules for simulation code

- **Deterministic.** Randomness comes only from `random.ts`; time comes only from counters the simulation advances as it steps. A `Math.random`, `Date` or `performance.now` read inside simulation code is a defect to fix, not a pattern to copy. Only what changes city state draws from the simulation's stream, tools and disasters included; the UI's own randomness, such as picking a new seed, comes from `uiRandom.ts`.
- **No DOM.** No `window` or `document` in simulation modules.
- **Simulation modules** are every file the simulation (`simulation.js`), the map generator (`mapGenerator.js`) or a map-editing tool (`cityTools.ts`, and every `*Tool.js`) imports, directly or not. `test/simulationImports.ts` walks that graph with the TypeScript checker and fails on any global but a short list of pure built-ins, on any `Math` function outside the portable ones, and on `**`, a package import or a dynamic import.
- **Portable arithmetic.** No transcendental `Math` functions (`sqrt`, `pow`, `sin`, `log`…) in simulation code: their results can differ between runtimes. Arithmetic is fine, and so are the `Math` functions whose results are exact everywhere, which `PORTABLE_MATH` in `test/simulationImports.ts` lists. The C# port mirrors each: `Math.trunc` copies C's conversion to a whole number, which drops the fraction toward zero, as a C# `(int)` or `(long)` cast does, and JavaScript's `Math.round` sends halves toward +∞ rather than to even. `Math.fround` rounds to the nearest IEEE single, as a C# `(float)` cast does. It reproduces the original's float arithmetic where a rule depends on it, provided every float operand and the result of each single `+`, `-`, `*` or `/` is wrapped in it: `Math.fround(Math.fround(a) * Math.fround(b))` is the float product, but `Math.fround(a * b + c)` is not the float sum of a float product.
- **Rule changes are deliberate.** The original's numbers are tuned against each other. A change to how the city behaves is named as such in its commit, never folded into a refactor. Each fixture's log pins its state hash as built and after a fixed run, as checkpoints that `test/goldenHashes.ts` replays. A change to a fixture's commands, to saved state or to a rule moves them, and that commit updates them and regenerates the conformance files (`npm run conformance`); a refactor that moves one is a defect. A run hash that moves while the built hash holds is a change to how the city behaves. The playthrough's golden checkpoints and log (`e2e/goldenPlaythrough.json`, rewritten by `npm run e2e:golden`) move for the same reasons, and for a change to a stage, to the commands or to how the game turns input into them; the commit that rewrites them says why.

## The original as reference

The original C/C++ source is the behavioural reference: <https://github.com/SimHacker/micropolis>, engine in `MicropolisCore/src/MicropolisEngine/src/`. The behaviour of the original's windows, such as the budget window's sliders, lives in the older C and Tcl version under `micropolis-activity/src/sim/` (`w_budget.c`, `w_sim.c`) and its Tcl scripts. This port follows it closely, function by function — for example `boatSprite.js` mirrors `doShipSprite` in `sprite.cpp`. When something behaves oddly, compare against the original before calling it a port bug: much odd behaviour is faithful to 1989, such as ships that wander the channel at random and wreck at dead ends.

Where the original's behaviour is undefined in C, the port keeps defined, portable behaviour and names the divergence in a comment at the code. Implementation-defined integer narrowing is matched.

## Code style

- Client modules are TypeScript, and so is every new module. Legacy simulation modules stay JavaScript, since the C# port retires them.
- The client works on the DOM directly, through the helpers in `domElements.ts`. `test/noJquery.ts` fails on any module under `src/` that imports jQuery.
- JavaScript modules name the file extension in their imports (`./tile.ts`, `./budget.js`); webpack's `extensionAlias` resolves both. TypeScript modules import TypeScript files without an extension (`./tile`), because `tsconfig.json` rejects a `.ts` suffix, and name it for JavaScript files (`./simulation.js`).
- `tsconfig.json` is strict, including `noUnusedLocals` and `noUnusedParameters`.
- Every source file keeps the GPL and Micropolis header comment at the top, new files included, C# and C as well.
- C#: block-scoped namespaces, explicit types rather than `var`, and nullable reference types; `server/Directory.Build.props` treats warnings as errors. Tests are MSTest, named `Method_Scenario_Expectation`.

## Hard Rules — Stop and Ask

If any of these arise, **stop immediately** and ask for guidance before continuing:

1. **Architectural dead-end**: the implementation cannot be solved cleanly. Explain the constraint and suggest clean alternatives.
2. **Hacky path**: mid-implementation you realise the approach involves workarounds or quality compromises. Discard it and propose the clean path. No sunk cost fallacy, no "just make it work for now".
3. **Against the direction**: the right implementation contradicts the Direction section or settles an Open decision. Raise it first; don't drift silently.
