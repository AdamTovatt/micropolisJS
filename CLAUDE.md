# CLAUDE.md

## Project Overview

A continuation of [micropolisJS](https://github.com/graememcc/micropolisJS), Graeme McCutcheon's hand-written JavaScript/HTML5 port of Micropolis — the GPL release of the original 1989 SimCity. A 120×100 tile city, drawn on a canvas in the browser. Every city is simulated on the game's server, shared by every player in it, and kept in the server's store; with no server answering, the page says so and offers no game.

This repository is Adam's continuation. The aim is to grow it from a faithful single-player port into the foundation of a multiplayer city builder with a richer simulated world. The **Direction** section below is the source of truth for where the code is heading.

| Component   | Technology                                                                         |
|-------------|------------------------------------------------------------------------------------|
| Language    | TypeScript in the browser; C# on .NET 10 for the server and the game rules          |
| Bundler     | webpack 5 + ts-loader, entry `src/micropolis.ts`, output `dist/`                   |
| UI          | plain DOM windows in `index.html`, on `windowBase.ts`; the map drawn with WebGL2   |
| Server      | ASP.NET Core on .NET 10, `server/Micropolis.slnx`; EasyReasy.Auth for tokens; SQLite through EasyReasy.Database for cities |
| Tests       | Jest + ts-jest, `test/*.ts`; MSTest, one test project per C# project               |
| Persistence | on the server, SQLite through EasyReasy.Database (`CityStore`), its schema migrated by DbUp, in the save format of `SavedGame` in `server/Micropolis.Rules`, where Save keeps a city; Download gives the player a city's save as a file, and Load starts one as a new city; the browser keeps in `localStorage` the cities it played, the player's session and settings (`src/storage.ts`) |

## Direction

Work that pulls against this needs Adam's go before it starts.

1. **A deterministic, headless simulation.** The simulation runs without a host or a DOM, advances by explicit steps rather than wall-clock time, and produces the same city from the same seed and the same sequence of player commands. Everything below builds on this.
2. **Server-authoritative multiplayer on a C# server.** The server owns the simulation. Browsers send commands ("road from A to B", "set tax to 9%") and render the state the server sends back. A player edit is a command the simulation applies, never a direct write to the map from UI code. Every player has the same powers: any player can issue any command, and the simulation never branches on who sent one.
3. **The C# code is the only home of the game rules.** Everything that changes or computes city state is C#, in `server/Micropolis.Rules`: the simulation, sprite behaviour, map generation and the random stream, applying and validating commands, answering queries, save and load. Command logs are both the end-to-end suite and the conformance suite, replayed headless in C#. Anything in the simulation that another language can't reproduce bit for bit is a defect.
4. **The browser is the client.** It draws tiles and sprites, animates tiles, captures input (tool choice, the hover box, turning drags into tile paths) and shows the windows. It changes city state only by sending commands. Map overlays and query-tool data come from the server on request.
5. **A modernised client.** Client code is TypeScript and works on the DOM directly, without jQuery.
6. **Gameplay improvements on top of the original rules**, such as ships that sail to the seaport instead of wandering the channel at random. They are built in the C# simulation, the one place each rule is written.
7. **Longer horizon, not planned in detail:** a richer generated world (climate and weather driven by parameters, natural resources, choosing where to found a city), several cities linked by road and rail, individually simulated residents, and LLM-driven notable residents whose behaviour may later be distilled into a small model of our own.

### Open decisions

Ask before writing code that settles an open decision; record the decision under Decided when it is made.

#### Decided

- **Multiplayer shape.** One shared city, run in real time by several mayors, each with every power a single player has: any player can build, bulldoze, set taxes and the budget, trigger disasters, pause and change the speed. Pause and speed are commands like any other and apply to everyone. The simulation never branches on who sent a command.

## Commands

```bash
npm install
(cd server/Micropolis.Server && dotnet run)   # server and client together: open http://localhost:5180
npm run dev              # webpack-dev-server on http://localhost:44903, the client alone: it plays on a server on :5180, and says it isn't answering without one
npm run build            # production bundle into dist/
npm run watch            # development bundle into dist/, rebuilt on each change
npm test                 # Jest
npm run test:watch       # Jest, run again on each change
npm run test:coverage    # Jest, with a coverage report of src/ in coverage/
npx jest test/money.ts   # one test file
npm run lint             # ESLint over src/, test/, e2e/ and the build config
npm run typecheck        # tsc over every TypeScript file in the repository, writing nothing
npm run e2e              # the end-to-end playthrough in headless Chromium, against the server's Debug build; report in e2e-report/
npm run e2e:golden       # run the playthrough to rewrite its checkpoints and log, e2e/goldenPlaythrough.json, if it passes
npm run record           # record again, from the server's Debug build, what the client's tests play back (test/recordings/)
npm run benchmark        # time the C# simulation and measure its state-message bytes on the fixtures, rewriting docs/benchmarks.md
npm run benchmark:render # measure the map's frames a second as the cars on it grow, in headless Chromium, printing a table (Rendering, below)
dotnet build server/Micropolis.slnx   # the C# solution
dotnet test server/Micropolis.slnx    # MSTest
dotnet run --project server/Micropolis.Headless -- --fixture town --steps 3000   # headless run: prints the state hash, year, population, funds
dotnet run --project server/Micropolis.Headless -- --log session.json            # replay a command log and check its checkpoints
dotnet run --project server/Micropolis.Headless -- --write-fixtures              # regenerate the fixtures' logs and saves and the conformance goldens (conformance/README.md)
pytest art/tools/tests   # the art build's tests, from a virtual environment of art/requirements.txt (art/README.md); --renders also runs the join again from art/painted/built/, where the renders say which donor gives each pixel
```

`dotnet run` in `server/Micropolis.Server` is the dev command, and `remote-claude.json` binds the dev-server button to it. The server listens on :5180, and SpaProxy starts `npm run dev` unless something already answers on :44903, then sends the browser there; whatever answers on :44903 is the client it uses. webpack-dev-server proxies `/api` and `/ws/city` to the server, and accepts any Host header, so a reverse proxy can front it under another name. The server will not start without three settings, which development takes from `Properties/launchSettings.json`: `JWT_SECRET`, at least 32 bytes; `TRUSTED_PROXIES`, the addresses of the reverse proxies in front of the server, separated by commas, or `none`; and `CITY_DATABASE`, the SQLite file it keeps its cities in, relative to the content root or absolute, which development puts at `.cities/cities.db` in the repository root (`.cities/` is ignored by git). The server makes the file, and its directory, if they don't exist, and brings its schema up to date as it starts; a file it can't open or migrate stops it. Behind a proxy it does not trust, the server sees every player at the proxy's address, and they share one sign-in rate limit. `CITY_CLOCK=manual`, which only a Debug build accepts (`dotnet build` and `dotnet run` build Debug; `dotnet publish` builds Release), runs the cities on a clock only the debug channel moves, for the client's tests. `dotnet publish` runs `npm ci` in the repository root, which deletes and reinstalls `node_modules`, then `npm run build`, which overwrites `dist/`, and copies `dist/` into the published `wwwroot`, which the server serves.

The headless runner takes `--seed <n>` (a generated map) or `--fixture <name>` (the fixture's committed built save), `--speed slow|medium|fast` to override the saved speed, and `--steps <n>`; or `--log <file>` alone, a command log (`docs/command-log.md`), such as one the debug window downloads; or `--write-fixtures` alone. Arguments it can't run print the problem and the usage, with exit code 2.

Node 24 or later (`engines` in `package.json`), and for `server/` the .NET SDK `global.json` pins, or a later one of the same major and minor version, which CI installs from the same file. CI (`.github/workflows/ci.yml`) runs on every push and pull request: one job runs `npm ci`, then build, test, lint and typecheck, on Node 24; another checks `conformance/random.json` against the program that writes it, then builds and tests the C# solution, which reads the conformance files as committed and fails unless the fixture tool writes them as committed, then runs in Release the tests only a Release build can settle (category `ReleaseBuild`), runs the benchmark for a few steps, checking only that it writes its table, and runs the client's tests that start the server it built, `test/citySource.ts` and `test/sharedCity.ts`, with `MICROPOLIS_SERVER_TESTS=1`; without it, as in the first job, they skip the server. Then it records the client's test streams again from that build (`npm run record`) and checks they are committed as it writes them; the first job's tests play back the committed ones. Locally, `dotnet build server/Micropolis.slnx` first, since those tests and `npm run record` run that build. After the first, a third builds the C# solution and runs the end-to-end suite, uploading its report whether it passed or not, and the traces of the tests that failed when one did. A fourth installs `art/requirements.txt` on Python 3.12 and runs the art tools' tests, which run the atlas build again from the committed painted layers and fail unless what it writes under `images/` is committed as it writes it, check the tables of designs in `art/tools/designs.py` against the painted layers, and check the painted single tiles against the committed layers the paint build's join works from, `art/painted/built/`; the join itself reads the renders, which git ignores, so its test runs by hand with `--renders` (`art/README.md`).

`npm run e2e` serves a production build with webpack on port 8181 (`E2E_PORT` moves it) and never reuses a server already there. A spec that plays the page past signing in plays against a game server of its own, never one already on the machine, such as this checkout's dev server on :5180: `e2e/gameServer.ts` starts the server's Debug build for each spec file (`serverForTests`), as `test/helpers/testServer.ts` starts it, with a city database of its own on a port the system picks, and sends the page's requests to the game server's API and its city's socket there. A page that needn't ask for a name opens signed in as a player, who signs in once for every page of the spec's, so a spec's sign-ins stay within the server's limit on them from one address. So `dotnet build server/Micropolis.slnx` first: without that build they fail naming it. A spec of what the page does before it signs in refuses those requests (`blockNetwork` in `e2e/page.ts`), so no server answers. A test that fails leaves its trace in `e2e-results/`, which `npx playwright show-trace` opens. Playwright's Chromium comes from `npx playwright install chromium`.

The client's tests are TypeScript: ts-jest compiles them for Jest, and Playwright compiles `e2e/` without checking types. The build's ts-loader type-checks every TypeScript file in the repository, `test/` and `e2e/` included, so `npm run build` fails on a type error anywhere. The game's Settings window and the footers of the about and name-license pages show the build ID, `git rev-parse --short=12 HEAD`, or `unknown` outside a git checkout.

Open the game with `?debug=1` in the URL for debug mode (`ClientConfig.debug` in `clientConfig.ts`, the client's alone: a city on the server has no client debug mode): the FPS counter shows, the query window shows the raw values of the simulation's report on the tile in its debug rows, and `window.micropolisTestHook` (`testHook.ts`) is installed. `?seed=<n>` starts the splash screen on that seed's map instead of a random one, with or without debug mode; a seed that isn't a uint32 raises an alert and the map is picked at random. `?city=<id>` joins the city on the server with that id, without the splash screen; a city started on the server puts its id there, so the page's address invites another player in and a reload rejoins; the Online panel's invite link is that address with the city's id alone, none of the page's other options. An id that isn't one, or a city that can't be joined, raises an alert and takes the link out of the address, and the player chooses a city on the splash screen; with no server answering, the page says so and keeps the link, which trying again follows. All three are read by `urlOptions.ts`.

### End-to-end suite

`e2e/playthrough.spec.ts` plays one city from a fixed seed through an ordered list of stages (`e2e/stages.ts`), the way a player would: real mouse and keyboard on the canvas and the windows, through `e2e/player.ts`. Adding a stage is the normal way to cover a new feature; a stage builds only on the site `SITE` names, which it may widen, and which the first stage checks is clear land on the seed's map, or where it chooses from the city's state. The fire stage does the latter: wherever the random stream lands the fire, it reads the burning tile from the save and builds a fire station whose cover reaches it at the strongest, with a road and a power line to the grid (`e2e/stationSite.ts`), panning the view with Space and the mouse to reach them. Where a station looks for its road, and the cover it would give the fire with its road on each tile there, are the rules' to say, so the stage asks the game server's debug channel for them at each site it considers. So a rule change that moves the stream moves only the goldens, unless it lands the fire where no such site is near, and then the stage fails naming the fire. The city runs on the game server, whose cities run on the server's own clock, and the test hook holds its step driver for the whole run, through the WebSocket source's asynchronous driver channel (`CityDriver` in `citySource.ts`), which the server's debug channel answers, and which is not the game's pause. While it is held, the game's tick still reads the mouse and keyboard, but sends no tool paths, and the source applies no commands: the runner does both after each action with the hook's `applyInput()`, so each action becomes the same commands on every run. The runner moves the city on only through the hook's `advance(n)`, which sends the input first, then has the source apply the commands and take the steps, and fails when city time falls short of the steps taken, as `CityTimeModel` in `Micropolis.Rules` models it. The source sends the state those steps changed before the advance resolves. So every input lands between the same two steps on every run. Each stage ends in a checkpoint: its step count, the commands applied so far, its state hash, a screenshot and the save, which the report (`e2e-report/index.html`) shows in stage order under the build ID and seed. The runner takes the city's state hash from the game server's debug channel, as the rules compute it, and checks it against the stage's golden checkpoint in `e2e/goldenPlaythrough.json` (`e2e/goldenPlaythrough.ts`); a checkpoint whose hash, step or commands differ fails the run, which carries on so the report is complete, and the failure, at the top of the report too, names the first stage that diverged. A stage with no golden checkpoint fails the same way, so a new stage is pinned with `npm run e2e:golden`, which writes the file only from a run that passed: every stage, its command log and the server's own driver. The screenshots are for looking at, never compared by the suite. The page's date is fixed for the run, and the client's tile animation and blink take their frame from it, and the cars their place, each at the start of its route, which each checkpoint checks through the test hook, failing the run if no stage's map view shows a car; the runner brings the view to the same origin on every run by panning it with Space and the mouse, the pointer dragged by the exact distance in CSS pixels to the origin, which it checks it reached, never with the scroll keys, which move the view for as long as they are down, and then puts the pointer back where it had last been moved (`showTiles` in `e2e/player.ts`); and nothing that closes on wall time is left closing at a screenshot: each dismisses the notification bar and the tool toast through the test hook first, and no stage ends while the disaster view counts down to closing. So a stage's screenshot is the same on every run and two builds' screenshots can be compared pixel for pixel. Each reload ends a session, as the end of the stages does: the page leaves the city, the runner waits until the server lists the player offline (`untilOffline` in `e2e/gameServer.ts`), which it does only once the player's leaving has saved the city to the store and unloaded it, and the page opens again at the city's link, which joins the city and loads it from the store; the page holds its driver as it starts (`holdAtStart` in `testHook.ts`, asked for before the page loads), so the hold reaches the server before the join and the city is held from its first step. The runner downloads each session's command log from the debug window and joins them in order into the run's log from the seed (`joinSessions` in `test/helpers/commandLog.ts`), which needs no entry for a load, since a load is transparent. The server logs a command under the id of the player who sent it, new at each sign-in, so the run names its players by when each first appears in its log (`namedByAppearance` in `e2e/goldenPlaythrough.ts`). The run's log must be the golden file's, and the C# replays that log headless to every checkpoint: the game's own with every other log, from its copy in `conformance/logs/`, and each stage's in `GoldenPlaythroughTests`, as `docs/command-log.md` describes. After the stages the runner releases the driver, so the server steps the city on its own clock, and waits on city time; a run whose step count depends on wall time has no reproducible state, so the report shows a screenshot of it and no save. The runner finds tiles on screen from the view's origin, snapped to whole device pixels as the game draws the map, and the tile width at the view's zoom, not through the game's own pointer-to-tile mapping, which is under test; after a zoom with a tool held, it checks the game draws the hover box on the tile it finds under the pointer. The playthrough runs at the 16 pixels a tile the game opens at, but for a stage that zooms in with the wheel and the keys, builds, and zooms out again.

## Architecture

### Layers

- **Simulation** — `server/Micropolis.Rules`, which runs without a host. `Simulation` orchestrates (with `Simulation.Commands.cs` and `Simulation.Queries.cs`); the subsystems are `MapScanner`, `Residential`, `Commercial`, `Industrial`, `Road`, `Transport`, `PowerManager`, `Traffic`, `Stadia`, `MiscTiles`, `EmergencyServices`, `Valves` (residential/commercial/industrial demand), `Census`, `Budget` (funding services through `ServiceFunding`), `Evaluation`, `DisasterManager`, `BlockMapUtils` and `CityStatus` (the advisor conditions and the city status record). `Records` builds the evaluation, budget and settings records the windows show. `CommandReader` validates the commands, and `Queries` validates and answers the queries, on the checks in `Validation`.
- **Game and UI** — `game.ts` shows a city a source has started: the canvas and the windows (`*Window.ts`), drawn from the client's copy of the city. It runs two loops: `tick` (`setTimeout(0)`, which hands each tick to the controls) and `animate` (`requestAnimationFrame`: painting the latest state). The controls (`GameControls` in `gameControls.ts`) are what the player's mouse, keyboard and windows do, read through the parts the game gives them, so Jest tests them under Node with stand-ins for those parts: each tick they scroll the view for the keys held, take Escape, send the tool paths drawn since the last tick, which they leave to the end-to-end runner while that holds the step driver, and place this player's hover box on the tile under the pointer, worked out once a tick for the box drawn and the box the other players are told of alike; and they open the windows the player asks for and act on the choices those close with. `InputStatus` (`inputStatus.ts`) keeps one pointer position and the tool chosen, which it checks against the tool names as it reads the tool buttons, failing on a button that names none or gives no whole number of tiles for its size, and on a tool a player may hold that no button offers, and announces the player's requests and tool clicks as events. The game follows whether the player can see the city as the tab's visibility changes or a resize shows or hides the screen-too-small overlay, and the controls show the other players this player's hover box only while they can. `windowManager.ts` shows the windows one at a time, each built on the plain-DOM base in `windowBase.ts` by extending `ClosableWindow`, which is typed by the arguments a window opens with and the choice it closes with: opening a window returns a promise of the player's choice, and the manager lets go of the input as the window closes, before the choice arrives, so a choice may open another window. A window that shows city figures opens on a plain record the simulation produces or on a query's answer, never on simulation objects, and turns any codes in it into text through `text.ts`. The budget window opens on the budget record, which places its sliders, and shows every figure from the answer to a `budgetForecast` query, which it asks through a `QuerySource` when it opens, on Reset and each time a slider moves. The settings window opens on the settings record beside the settings the client keeps, which the controls build: the auto-bulldoze preference, the share of the trips that become cars and the seed. A window closes with the player's choices as plain data. A window showing holds the keyboard and mouse; no window holds the city. While it does, the game takes no key but Escape, so the window's sliders, selects and inputs have the keyboard, and Escape is latched until the game's tick takes it, so a tap between two ticks still closes the window. The year-end budget never waits for the player (see `Budget.DoBudgetNow`): with auto-budget off, or when auto-budget couldn't cover the services, the Budget button marks the review due until this player opens the budget window, from it or from the notification bar, which offers the review while no news shows (an offer is a hint, which news replaces and which takes no message's place), and the window's changes are a `setBudget` command. The budget window never opens unasked, since in a shared city it would open for every player at once. `windowCommands.ts` turns the windows' choices into commands. Milestones are good-news notifications, not windows. A notification with a place says "Go there" beside its text, and a click on the bar centres the view there; the Last event button beside the bar centres it, once, on the last news the bar announced with a place, or, for news that follows a monster or a tornado, on where that sprite is now while one of its type is on the map (`LastEvent` in `news.ts`). The minimap (`minimap.ts`) is a panel at the foot of the right column, not a window: the whole map a square a tile, each tile in the average colour of its 16 px tile, drawn from the client's copy of the map, with the view's rectangle over it, and a click or a drag on it centres the view there. The HUD (`#hud` in `index.html`) is dark see-through panels in regions round a clear middle, laid out by grid and flex so a panel that grows pushes its neighbours and none has a fixed height: the city's figures in a bar along the top left; the left column under it, the menu, a list with an icon for each item and Pause apart, and the demand meter, a dark track for each kind of zone, with the disaster view at its foot, under a title naming what it shows; the middle, the notification bar with Last event beside it at its top and the tools in a dock of two rows of eight at its foot; and the right column, the whole height of the screen, who is online with the invite button, the overlay picker with its legend, the status, the activity and, in debug mode, the debug panel, with the minimap at its foot. ### The simulation cycle

`Simulation.Step` is one loop, as `simLoop` in the original: `SimFrame` gates on the game speed, then every sprite moves. The gate is the saved `SpeedCycle` counter, which lets a phase through on every 5th step at slow speed, every 3rd at medium and every step at fast. A paused simulation's step does nothing. The step count, never wall time, advances the city. Each step that passes the gate runs `Simulate`, which advances one phase of a 16-phase cycle:

| Phase | Work |
|-------|------|
| 0     | advance the city time and the sim cycle, set the demand valves, clear the census |
| 1–8   | scan one eighth of the map's columns each, calling the tile handlers |
| 9     | census, tax collection and city evaluation at their frequencies |
| 10    | decay the rate-of-growth and traffic maps, send advisor messages |
| 11–15 | power scan; pollution, terrain and land value; crime; population density; fire coverage and disasters, then publish the city status record |

How often phases 11–15 run depends on the game speed (`SpeedPowerScan` and its siblings in `Simulation`), so speed changes simulation results. It is simulation state, not a display setting.

### Tile handlers

Subsystems register handlers with `MapScanner.AddAction`, by tile value or by a test of the tile, from their `RegisterHandlers`, all called as the `Simulation` is built. During phases 1–8 the scanner calls the handler for every matching tile with the map, the tile's position and a `SimData` (from `ConstructSimData`), which carries the census, budget, block maps, the random stream, the sprite manager and the other managers.

### State

- `GameMap` holds the tile grid. `Tile` is a tile's value plus flags (`TileFlags`: powered, conductive, burnable, bulldozable, zone centre…). `TileValues` names every tile id (`RIVER`, `CHANNEL`, `PORT`…), as the client's `tileValues.ts` and `tileFlags.ts` do.
- `Simulation.BlockMaps` holds coarse overlays at block sizes 2, 4 or 8 (`BlockMap`): land value, pollution, crime, traffic density, population density, police and fire coverage, rate of growth. The `BlockMaps` constructor gives each its block size and range.
- `Simulation.Random` is the simulation's random stream (`RandomStream`), seeded from the game seed. The map generator draws from the same seed's map stream, so one seed reproduces map and city. The `RandomStream` header specifies the stream, and `conformance/random.json` holds reference vectors computed by the reference C implementation, which its tests read in place.
- A stateful component's `Save` and `Load` write and read its fields under its own key of the save. What the scans derive is saved under `scannedState` instead, through `SaveScan` and `LoadScan`: the census has both pairs, and the power manager, which holds only scan results, has only the scan pair. A save holds the complete simulation state, the stream's included, so a loaded city continues exactly as it would have without the save; `docs/state-hash.md` lists every key, and a field the simulation adds is saved and listed there too. `Simulation.Trips` alone is not: the rules never read it, and it only offers trips for the client's cars. `Simulation.NewCity` starts a new city from a seed, and `Simulation.FromSave` builds one from a saved state, without scanning. `SavedGame` in `server/Micropolis.Rules` writes a save's text, with the city's name and the save's version beside the simulation's state, and reads one, migrating a save from an older version first; `CityStore` keeps the text on the server. It reads saves from `OldestVersion`, 5, the first that holds the complete state. The version is one past the last of the migration steps in `Upgrades`, each of which upgrades a save from its place in the list, so a step only ever goes at the end. A change to saved state appends a migration step, which bumps the version, changes the save model to read it, leaves the save a command log starts from in the version its `saveVersion` names, which the replay upgrades through the same steps (`docs/command-log.md`), regenerates the fixtures' goldens (`--write-fixtures`), records the client's test streams again (`npm run record`) where what the server sends moved, and adds a sample save of the new version, written by the game of that commit, to `conformance/saveVersions/` (`conformance/README.md` says how), all in the same commit.

### Events

Each component that emits events holds an `EventEmitter`, with `AddEventListener` and `Emit`, which take an event's key. `RulesEvents` in `server/Micropolis.Rules` declares every event once, as a key holding its name and the type of its payload (`EventName<TPayload>`, or `EventName` for an event without one), so a listener receives that type and an emitter can only send it: the protocol's record where the payload is what a state message carries or a record of the protocol's, one value where it is one, and otherwise a small record of its own, never JSON. JSON is only at the edge: the emitter's `Observer` sees each event's name and its typed payload, which `LogReplay` and the tests that read events write as the protocol does. Event names live in `Messages`, and in the client's `messages.ts` as the server sends them, each a string no other message shares, since the client tells events apart by the string; `MessagesTests` fails on two names that share one, and `test/messages.ts` on two of the client's. Subsystems emit, `Simulation` re-emits upward, and the server's city host turns what it hears into state messages for the client: the simulation never calls UI code. The trips `Trips` offers for the client's cars are the one exception, a plain C# event: the emitters' events are what `LogReplay` records into the event goldens, which trips are no part of. The client's input announces what the player does through its own base, `Emitter` in `emitter.ts`, which is typed by a map of its events' names to what each carries, under names of the client's own in `uiMessages.ts`, beside the notices the page shows of its own accord; no city sends them, and `test/messages.ts` holds them apart from the city's names too.

A condition that holds over time (power load against capacity, a demand cap, an advisor warning) is state, published each cycle in the `CITY_STATUS_UPDATED` record, which reaches the client as a `status` message that `statusPanel.ts` renders. A `FRONT_END_MESSAGE` notification announces a condition or a one-off event and then times out; the record is what shows a condition for as long as it holds. The record is built each cycle and not saved, but its sources are: the power figures from the last power scan, and the cap flags from the valves.

### Sprites

`SpriteManager` and the `*Sprite.cs` files: train, ship, plane, helicopter, monster, tornado and explosion. Sprites move once per simulation step (`Simulation.Step` → `SpriteManager.MoveObjects`), at the same rate whatever the game speed, and draw from the simulation's stream, so their behaviour, including the map damage a crash, monster or tornado causes, is part of the deterministic simulation.

### Commands

Every change a player makes to the city is a command: plain JSON, defined in `protocol.ts` as part of the multiplayer protocol. UI code never writes to the map, the budget or the managers. `Simulation.ApplyCommands` validates each command (`CommandReader`) and applies it, separately from `Step`. A rejected command changes nothing. Each command's result, with the player who sent it, its outcome and the reason for a rejection, is emitted as `COMMAND_RESULT`; the simulation never branches on the player. `CommandQueue` in `server/Micropolis.Server` drives a city's simulation: commands queue as they arrive and apply in arrival order whenever the queue applies them, every turn of the city's loop whether or not the city is stepping, and each is stamped with the index of the step it precedes. The queue hands each stamped command, and each step before it is taken, to a recorder: `CommandRecorder` records the city's command log (`docs/command-log.md`), with a checkpoint of the state hash every 3,600 steps, which the debug window downloads and the headless runner replays. The UI turns clicks and drags into tile paths: `dragPath.ts` gathers the tiles the tool reaches, filling in those a fast mouse skips, and each tick sends a drag's new tiles as one tool command.

A query asks the simulation about the city and changes nothing: plain JSON, defined in `protocol.ts` beside the commands. `Simulation.AnswerQuery` validates it (`Queries`) and answers at once, with a copy of what it reads; it never draws from the stream and is never logged. An `overlay` query names a layer, one of the block maps the player can see or the power grid, and is answered with the layer's block size, range and values. The simulation emits `OVERLAY_UPDATED` with a layer's name once the phase that recomputes it has run (each `OverlayLayer`'s phase in `Queries`), which reaches the client as an `overlayUpdated` message, and an overlay showing that layer asks again. A `tileReport` query names a tile, and is answered with the tile's raw values and its category, the table of the original's `doZoneStatus`; the client sorts the values into the bands the query window shows. A `budgetForecast` query names the funding of some services and the tax rate, and is answered with the budget record and what the year end would cost, collect and leave at them, as `Budget.Forecast` works it out, collecting at a tax rate named what the year's collection would take from the census now. A `mapPreview` query names a game seed, and is answered with the map a new city on it starts on, before any city has started too.

### Tools

`*Tool.cs` on top of `CityTool`; `CityTools` builds the tools that change the city, with their costs, which the simulation applies tool commands with. A tool command applies its tool at each tile of its path in order, as one click each: the tool stages its edits in a `WorldEffects`, drawing from the stream as it goes, checks the funds, then writes the staged tiles to the map and charges the budget. The query tool (`queryTool.ts`) belongs to the UI: it sends a `tileReport` query for the tile clicked, and the query window shows the answer. It asks, as the overlay picker does, through a `QuerySource` (`querySource.ts`), which the city source is.

## Rules for simulation code

Simulation code is `server/Micropolis.Rules`, which holds the game rules and nothing that runs them: it has no ASP.NET dependency, and the server, the headless runner and the tests each host it.

- **Deterministic.** Randomness comes only from `RandomStream`; time comes only from counters the simulation advances as it steps. A clock, `Random` or anything read from the machine inside simulation code is a defect to fix, not a pattern to copy. Only what changes city state draws from the simulation's stream, tools and disasters included; the client's own randomness, such as picking a new seed, comes from `uiRandom.ts`.
- **Checked by its tests.** `PortableRulesTests` holds the compiled `Micropolis.Rules` to these rules through its metadata: no clock, `Random` or `HashCode`, nothing of `Environment` but the thread id the compiler's iterators read, and no `Math` function outside the portable ones, nor a generic math interface that offers the others. Beside it, `SavedFieldsTests` fails on a field a component holds but neither saves nor explains, and `DeterminismTests` on two runs from one start that differ.
- **Portable arithmetic.** No transcendental `Math` functions (`Sqrt`, `Pow`, `Sin`, `Log`…) in simulation code: their results can differ between runtimes. Arithmetic is fine, and so are the `Math` functions whose results are exact everywhere, which `PortableMath` in `PortableRulesTests` lists. A C# `(int)` or `(long)` cast drops the fraction toward zero, as C's conversion to a whole number does, and `JsMath.FloorDiv` divides rounding toward −∞, for the rules whose division of a negative number floors. `JsMath.Fround` rounds to the nearest IEEE single, as a C# `(float)` cast does. It reproduces the original's float arithmetic where a rule depends on it, provided every float operand and the result of each single `+`, `-`, `*` or `/` is wrapped in it: `Fround(Fround(a) * Fround(b))` is the float product, but `Fround(a * b + c)` is not the float sum of a float product.
- **Rule changes are deliberate.** The original's numbers are tuned against each other. A change to how the city behaves is named as such in its commit, never folded into a refactor. Each fixture's log pins its state hash as built and after a fixed run, as checkpoints that `LogReplayTests` replays, and the fixture tool's other goldens (Headless, above) pin what checkpoints can't show. A change to a fixture's commands, to saved state or to a rule moves them, and that commit regenerates them all with `--write-fixtures`, whose tests fail until it has. A change to a rule or to saved state moves the client's test streams too, which the server's rules produce, so the same commit records them again (`npm run record`). A refactor that moves one is a defect. A run hash that moves while the built hash holds is a change to how the city behaves. The playthrough's golden checkpoints and log (`e2e/goldenPlaythrough.json`, rewritten by `npm run e2e:golden`) move for the same reasons, and for a change to a stage, to the commands or to how the game turns input into them; the commit that rewrites them says why, then runs `--write-fixtures`, which copies the log to `conformance/logs/playthrough.log.json` and fails while the golden log no longer replays, so `npm run e2e:golden` runs first.

## The original as reference

The original C/C++ source is the behavioural reference: <https://github.com/SimHacker/micropolis>, engine in `MicropolisCore/src/MicropolisEngine/src/`. The behaviour of the original's windows, such as the budget window's sliders, lives in the older C and Tcl version under `micropolis-activity/src/sim/` (`w_budget.c`, `w_sim.c`) and its Tcl scripts. The rules follow it closely, function by function — for example `TrainSprite` mirrors `doTrainSprite` in `sprite.cpp`, and a rule changed on purpose says so in a comment at the code. When something behaves oddly, compare against the original before calling it a port bug: much odd behaviour is faithful to 1989.

Where the original's behaviour is undefined in C, the rules keep defined, portable behaviour and name the divergence in a comment at the code. Implementation-defined integer narrowing is matched.

## Code style

- Client modules are TypeScript, which `test/clientImports.ts` enforces under `src/`.
- The client works on the DOM directly, through the helpers in `domElements.ts`. `test/noJquery.ts` fails on any module under `src/` that imports jQuery.
- TypeScript modules import each other without an extension (`./tileSet`), because `tsconfig.json` rejects a `.ts` suffix.
- `tsconfig.json` is strict, including `noUnusedLocals` and `noUnusedParameters`.
- A promise is awaited, handled, or marked `void` with a comment saying why nothing waits on it. ESLint's `no-floating-promises` and `no-misused-promises` fail on one that is none of these, under `src/`, `test/` and `e2e/`; the comment is the reviewer's to check.
- Every source file, TypeScript, JavaScript, C#, C, Python, HTML and CSS, opens with the GPL and Micropolis header in its language's comments, after a shebang line if it has one and, in a page, after the doctype, in one of two forms, whose text `test/headers.ts` holds. A new file takes the continuation's header, which opens "micropolisJS, continued by Adam Tovatt from Graeme McCutcheon's micropolisJS.". A file ported or converted from upstream's code, the C# ports of its modules and the TypeScript converted from its JavaScript among them, or split from such a file, takes the derived header, which keeps Graeme McCutcheon's line, "micropolisJS. Adapted by Graeme McCutcheon from Micropolis.", and adds the continuation's notice that it was modified. Where a file's ancestry isn't clear, it takes the derived one. Both go on with the GPL, EA and Micropolis text, which in a page names the license at upstream's site on GitHub Pages and in every other file at micropolisjs.graememcc.co.uk; the year is the one the continuation began. The test fails on a tracked file that opens with neither form, or carries both.
- C#: block-scoped namespaces, explicit types rather than `var`, and nullable reference types; `server/Directory.Build.props` treats warnings as errors, and has the build enforce the first two, which `server/.editorconfig` states, and check every doc comment and `cref` that exists, without requiring a comment on any member. Package versions live in `server/Directory.Packages.props`, never in a project. Tests are MSTest, named `Method_Scenario_Expectation`.

## Hard Rules — Stop and Ask

If any of these arise, **stop immediately** and ask for guidance before continuing:

1. **Architectural dead-end**: the implementation cannot be solved cleanly. Explain the constraint and suggest clean alternatives.
2. **Hacky path**: mid-implementation you realise the approach involves workarounds or quality compromises. Discard it and propose the clean path. No sunk cost fallacy, no "just make it work for now".
3. **Against the direction**: the right implementation contradicts the Direction section or settles an Open decision. Raise it first; don't drift silently.
