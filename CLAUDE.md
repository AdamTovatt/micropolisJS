# CLAUDE.md

## Project Overview

A continuation of [micropolisJS](https://github.com/graememcc/micropolisJS), Graeme McCutcheon's hand-written JavaScript/HTML5 port of Micropolis — the GPL release of the original 1989 SimCity. A 120×100 tile city, drawn on a canvas in the browser. With no server answering, the city is simulated in the browser and saved to `localStorage`; when the game's server answers, the city is simulated there, shared by every player in it, and kept in the server's store.

This repository is Adam's private continuation. The aim is to grow it from a faithful single-player port into the foundation of a multiplayer city builder with a richer simulated world. The **Direction** section below is the source of truth for where the code is heading.

| Component   | Technology                                                                         |
|-------------|------------------------------------------------------------------------------------|
| Language    | TypeScript in the browser, and JavaScript (ES5-style prototypes) in the legacy simulation modules; C# on .NET 10 for the server |
| Bundler     | webpack 5 + ts-loader, entry `src/micropolis.ts`, output `dist/`                   |
| UI          | plain DOM windows in `index.html`, on `windowBase.ts`; the map drawn with WebGL2   |
| Server      | ASP.NET Core on .NET 10, `server/Micropolis.slnx`; EasyReasy.Auth for tokens; SQLite through EasyReasy.Database for cities |
| Tests       | Jest + ts-jest, `test/*.ts`; MSTest, one test project per C# project               |
| Persistence | JSON in `localStorage` (`src/storage.ts`, the save format in `src/savedGame.ts`); on the server, SQLite through EasyReasy.Database (`CityStore`), its schema migrated by DbUp |

## Direction

Work that pulls against this needs Adam's go before it starts.

1. **A deterministic, headless simulation.** The simulation runs without a DOM (in Node, and in C# after the port), advances by explicit steps rather than wall-clock time, and produces the same city from the same seed and the same sequence of player commands. Everything below builds on this.
2. **Server-authoritative multiplayer on a C# server.** The server owns the simulation. Browsers send commands ("road from A to B", "set tax to 9%") and render the state the server sends back. A player edit is a command the simulation applies, never a direct write to the map from UI code. Every player has the same powers: any player can issue any command, and the simulation never branches on who sent one.
3. **The TypeScript simulation is the reference until the C# port replaces it.** Everything that changes or computes city state moves to C#: the simulation, sprite behaviour, map generation and the random stream, applying and validating commands, save and load. The port is correct when it reproduces the TypeScript simulation's state hash from the same seed, starting state and command log. Once it does, the TypeScript simulation is deleted and the C# code is the only home of the game rules. Command logs are both the end-to-end suite and the conformance suite: replayed headless and in the browser while the TypeScript simulation exists, and on the server after. Anything in the simulation that another language can't reproduce bit for bit is a defect.
4. **The browser is the client.** It draws tiles and sprites, animates tiles, captures input (tool choice, the hover box, turning drags into tile paths) and shows the windows. It changes city state only by sending commands. Map overlays and query-tool data come from the server on request.
5. **A modernised client.** Client code is TypeScript and works on the DOM directly, without jQuery. Simulation modules are not converted: the C# port retires them.
6. **Gameplay improvements on top of the original rules**, such as ships that sail to the seaport instead of wandering the channel at random. They are built in the C# simulation after the port, so each rule is written once.
7. **Longer horizon, not planned in detail:** a richer generated world (climate and weather driven by parameters, natural resources, choosing where to found a city), several cities linked by road and rail, individually simulated residents, and LLM-driven notable residents whose behaviour may later be distilled into a small model of our own.

### Open decisions

Ask before writing code that settles an open decision; record the decision under Decided when it is made.

#### Decided

- **Multiplayer shape.** One shared city, run in real time by several mayors, each with every power a single player has: any player can build, bulldoze, set taxes and the budget, trigger disasters, pause and change the speed. Pause and speed are commands like any other and apply to everyone. The simulation never branches on who sent a command.

## Commands

```bash
npm install
(cd server/Micropolis.Server && dotnet run)   # server and client together: open http://localhost:5180
npm run dev              # webpack-dev-server on http://localhost:44903, the client alone
npm run build            # production bundle into dist/
npm test                 # Jest
npx jest test/tile.ts    # one test file
npm run lint             # ESLint over src/, test/, headless/, e2e/ and the build config
npm run simulate -- --fixture town --steps 3000   # headless run: prints the state hash, year, population, funds
npm run simulate -- --log session.json            # replay a command log and check its checkpoints
npm run fixtures         # export each fixture's log to headless/fixtures/export/ (ignored by git)
npm run e2e              # the end-to-end playthrough in headless Chromium, against the server's Debug build; report in e2e-report/
npm run e2e:golden       # run the playthrough to rewrite its checkpoints and log, e2e/goldenPlaythrough.json, if it passes
npm run conformance      # regenerate the conformance files the TypeScript reference computes (conformance/README.md)
npm run record           # record again, from the server's Debug build, what the client's tests play back (test/recordings/)
npm run benchmark        # time the C# simulation and measure its state-message bytes on the fixtures, rewriting docs/benchmarks.md
dotnet build server/Micropolis.slnx   # the C# solution
dotnet test server/Micropolis.slnx    # MSTest
dotnet run --project server/Micropolis.Headless -- --fixture town --steps 3000   # the C# headless runner, with npm run simulate's options
dotnet run --project server/Micropolis.Headless -- --write-fixtures   # write every log in conformance/logs/ from the C# rules, the same as npm run conformance writes them
```

`dotnet run` in `server/Micropolis.Server` is the dev command, and `remote-claude.json` binds the dev-server button to it. The server listens on :5180, and SpaProxy starts `npm run dev` unless something already answers on :44903, then sends the browser there; whatever answers on :44903 is the client it uses. webpack-dev-server proxies `/api` and `/ws/city` to the server, and accepts any Host header, so a reverse proxy can front it under another name. The server will not start without three settings, which development takes from `Properties/launchSettings.json`: `JWT_SECRET`, at least 32 bytes; `TRUSTED_PROXIES`, the addresses of the reverse proxies in front of the server, separated by commas, or `none`; and `CITY_DATABASE`, the SQLite file it keeps its cities in, relative to the content root or absolute, which development puts at `.cities/cities.db` in the repository root (`.cities/` is ignored by git). The server makes the file, and its directory, if they don't exist, and brings its schema up to date as it starts; a file it can't open or migrate stops it. Behind a proxy it does not trust, the server sees every player at the proxy's address, and they share one sign-in rate limit. `CITY_CLOCK=manual`, which only a Debug build accepts (`dotnet build` and `dotnet run` build Debug; `dotnet publish` builds Release), runs the cities on a clock only the debug channel moves, for the client's tests. `dotnet publish` runs `npm ci` in the repository root, which deletes and reinstalls `node_modules`, then `npm run build`, which overwrites `dist/`, and copies `dist/` into the published `wwwroot`, which the server serves.

The headless runner takes `--seed <n>` (a generated map) or `--fixture <name>`, `--reseed <n>` to replace a fixture's stream, `--speed slow|medium|fast` to override the saved speed, and `--steps <n>`; or `--log <file>` alone, a command log (`docs/command-log.md`), such as one the debug window downloads.

Node 24 or later (`engines` in `package.json`), and the .NET 10 SDK for `server/`. CI (`.github/workflows/ci.yml`) runs on every push and pull request: one job runs `npm ci`, then build, test and lint, on Node 24, and checks that the files `npm run conformance` writes are committed as it writes them; another checks `conformance/random.json` against the program that writes it, then builds and tests the C# solution, which reads the conformance files as committed, then runs in Release the tests only a Release build can settle (category `ReleaseBuild`), runs the benchmark for a few steps, checking only that it writes its table, and runs the client's tests that start the server it built, `test/citySource.ts` and `test/sharedCity.ts`, with `MICROPOLIS_SERVER_TESTS=1`; without it, as in the first job, they skip the server. Then it records the client's test streams again from that build (`npm run record`) and checks they are committed as it writes them; the first job's tests play back the committed ones. Locally, `dotnet build server/Micropolis.slnx` first, since those tests and `npm run record` run that build. After the first, a third builds the C# solution and runs the end-to-end suite, uploading its report whether it passed or not, and the traces of the tests that failed when one did.

`npm run e2e` serves a production build with webpack on port 8181 (`E2E_PORT` moves it) and never reuses a server already there. The playthrough and the online spec play against a game server of their own, never one already on the machine, such as this checkout's dev server on :5180: `e2e/gameServer.ts` starts the server's Debug build, as `test/helpers/testServer.ts` starts it, with a city database of its own on a port the system picks, and sends the page's requests to the game server's API and its city's socket there. So `dotnet build server/Micropolis.slnx` first: without that build they fail naming it. The save-file and splash-screen specs refuse those requests, so the game plays single-player in the browser. A test that fails leaves its trace in `e2e-results/`, which `npx playwright show-trace` opens. Playwright's Chromium comes from `npx playwright install chromium`.

Tests are TypeScript and can import the legacy JavaScript modules: ts-jest compiles both for Jest, and Playwright compiles `e2e/` without checking types. The build's ts-loader type-checks every TypeScript file in the repository, `test/` and `e2e/` included, so `npm run build` fails on a type error anywhere. The game's Settings window and the footers of the about and name-license pages show the build ID, `git rev-parse --short=12 HEAD`, or `unknown` outside a git checkout.

Open the game with `?debug=1` in the URL for debug mode (`ClientConfig.debug` in `clientConfig.ts`, which the Worker and in-page sources pass on to the simulation's `Config.debug` in `config.js`; a city on the server has no client debug mode): an undefined event name in the simulation throws instead of warning, the FPS counter shows, the query window shows the raw values of the simulation's report on the tile in its debug rows, the splash screen offers "Load save file" for a save's JSON (such as an end-to-end checkpoint's), and `window.micropolisTestHook` (`testHook.ts`) is installed. `?seed=<n>` starts the splash screen on that seed's map instead of a random one, with or without debug mode; a seed that isn't a uint32 raises an alert and the map is picked at random. `?city=<id>` joins the city on the server with that id, without the splash screen; a city started on the server puts its id there, so the page's address invites another player in and a reload rejoins. An id that isn't one, a city that can't be joined, or no server answering raises an alert and takes the link out of the address, and the player chooses a city on the splash screen. All three are read by `urlOptions.ts`.

### End-to-end suite

`e2e/playthrough.spec.ts` plays one city from a fixed seed through an ordered list of stages (`e2e/stages.ts`), the way a player would: real mouse and keyboard on the canvas and the windows, through `e2e/player.ts`. Adding a stage is the normal way to cover a new feature; a stage builds only on the site `SITE` names, which it may widen, and which the first stage checks is clear land on the seed's map, or where it chooses from the city's state. The fire stage does the latter: wherever the random stream lands the fire, it reads the burning tile from the save and builds a fire station whose cover reaches it at the strongest, with a road and a power line to the grid (`e2e/stationSite.ts`), scrolling the view with the arrow keys to reach them. So a rule change that moves the stream moves only the goldens, unless it lands the fire where no such site is near, and then the stage fails naming the fire. The city runs on the game server, whose cities run on the server's own clock, and the test hook holds its step driver for the whole run, through the WebSocket source's asynchronous driver channel (`CityDriver` in `citySource.ts`), which the server's debug channel answers, and which is not the game's pause. While it is held, the game's tick still reads the mouse and keyboard, but sends no tool paths, and the source applies no commands: the runner does both after each action with the hook's `applyInput()`, so each action becomes the same commands on every run. The runner moves the city on only through the hook's `advance(n)`, which sends the input first, then has the source apply the commands and take the steps, and fails when city time falls short of the steps taken, as `CityTimeModel` in `Micropolis.Rules` models it. The source sends the state those steps changed before the advance resolves. So every input lands between the same two steps on every run. Each stage ends in a checkpoint: its step count, the commands applied so far, its state hash, a screenshot and the save, which the report (`e2e-report/index.html`) shows in stage order under the build ID and seed. The runner hashes the simulation's part of the save in Node with `stateHash.ts`, and checks it against the stage's golden checkpoint in `e2e/goldenPlaythrough.json` (`e2e/goldenPlaythrough.ts`); a checkpoint whose hash, step or commands differ fails the run, which carries on so the report is complete, and the failure, at the top of the report too, names the first stage that diverged. A stage with no golden checkpoint fails the same way, so a new stage is pinned with `npm run e2e:golden`, which writes the file only from a run that passed: every stage, its command log and the server's own driver. The screenshots are for looking at, never compared by the suite. The page's date is fixed for the run, and the client's tile animation and blink take their frame from it; the runner scrolls the view to the same origin on every run, whatever the timing of its key presses; and nothing that closes on wall time is left closing at a screenshot: each dismisses the notification bar through the test hook first, and no stage ends while the disaster view counts down to closing. So a stage's screenshot is the same on every run and two builds' screenshots can be compared pixel for pixel. Each reload ends a session, as the end of the stages does: the page leaves the city, the runner waits until the server lists the player offline (`untilOffline` in `e2e/gameServer.ts`), which it does only once the player's leaving has saved the city to the store and unloaded it, and the page opens again at the city's link, which joins the city and loads it from the store; the page holds its driver as it starts (`holdAtStart` in `testHook.ts`, asked for before the page loads), so the hold reaches the server before the join and the city is held from its first step. The runner downloads each session's command log from the debug window and joins them in order into the run's log from the seed (`joinSessions` in `commandLog.ts`), which needs no entry for a load, since a load is transparent. The server logs a command under the id of the player who sent it, new at each sign-in, so the run names its players by when each first appears in its log (`namedByAppearance` in `e2e/goldenPlaythrough.ts`). The run's log must be the golden file's, and the C# replays that log headless to every checkpoint: the game's own with every other log, from its copy in `conformance/logs/`, and each stage's in `GoldenPlaythroughTests`, as `docs/command-log.md` describes. After the stages the runner releases the driver, so the server steps the city on its own clock, and waits on city time; a run whose step count depends on wall time has no reproducible state, so the report shows a screenshot of it and no save. The runner finds tiles on screen from the view's origin and the tile width at the view's zoom, not through the game's own pointer-to-tile mapping, which is under test. The playthrough runs at the 16 pixels a tile the game opens at, but for a stage that zooms in with the wheel and the keys, builds, and zooms out again.

`e2e/saveFile.spec.ts` tests debug mode's "Load save file". `e2e/shadows.spec.ts` draws the map from a test atlas whose shadows overlap and reads the pixels back: the overlap shows the darker value, not the sum, and a map drawn again in part, around a tile whose shadow reaches into the blocks beside it, shows what the map drawn whole does, at one device pixel to the CSS pixel and at 1.1, where tiles' edges fall inside device pixels. `e2e/overlay.spec.ts` and `e2e/sprites.spec.ts` do the same for the map overlay, whose tint over each tile must match the tile's value in the save on the overlay's own colour ramp, and for a sprite, which must fill its square and be drawn again in part as drawn whole. `e2e/renderer.spec.ts` reads back the Screenshot window's pictures, the map on a screen of two device pixels to the CSS pixel, and the map drawn again after the browser loses and restores its WebGL context. `e2e/zoom.spec.ts` zooms with the pointer off the map, while a window holds the input and in the middle of a drag. `e2e/splashScreen.spec.ts` tests how the page starts: telling a browser without WebGL2 that the game needs it, waiting for the tile image, and reporting one that fails to load, or render art that fails to load or is past the browser's largest texture, waiting while the screen is too small to play, refusing a `?seed` that isn't a uint32, and the start form, where a city needs a name outside debug mode and one left unnamed in debug mode is MyTown. `e2e/onlineCity.spec.ts` plays the page online against a server of its own, whose cities run on a clock only the debug channel moves: the link a started city puts in the address, which a second player's page joins, a link the page can't follow, a city the server closes for failing, and a start the server fails.

## Architecture

### Layers

- **Simulation** — DOM-free. `simulation.js` orchestrates; the subsystems are `mapScanner.js`, `residential.js`, `commercial.js`, `industrial.js`, `road.js`, `transport.js`, `powerManager.js`, `traffic.js`, `stadia.js`, `miscTiles.js`, `emergencyServices.js`, `valves.js` (residential/commercial/industrial demand), `census.js`, `budget.js` (funding services through `serviceFunding.ts`, with `budgetRecord.ts`, the budget record the budget window shows), `evaluation.js` (with `evaluationRecord.ts`, the evaluation record the evaluation window shows), `settingsRecord.ts` (the settings record the settings window shows), `disasterManager.js`, `blockMapUtils.js`, `cityStatus.ts` (the advisor conditions and the city status record). `commands.ts` and `queries.ts` are simulation code too: how the commands are validated, and how the queries are validated and answered, on the checks in `validation.ts`, which the C# port reproduces.
- **Game and UI** — `game.ts` shows a city a source has started: the canvas and the windows (`*Window.ts`), drawn from the client's copy of the city. It runs two loops: `tick` (`setTimeout(0)`: the mouse and keyboard, then the tool paths drawn since the last tick, which it leaves to the end-to-end runner while that holds the step driver, then this player's hover box for the other players) and `animate` (`requestAnimationFrame`: painting the latest state). It tells the source whether the player can see the city as the tab's visibility changes or a resize shows or hides the screen-too-small overlay. `windowManager.ts` shows the windows one at a time, each built on the plain-DOM base in `windowBase.ts` by extending `ClosableWindow`. A window that shows city figures opens on a plain record the simulation produces or on a query's answer, never on simulation objects, and turns any codes in it into text through `text.ts`. The budget window opens on the budget record, which places its sliders, and shows every figure from the answer to a `budgetForecast` query, which it asks through a `QuerySource` when it opens, on Reset and each time a slider moves. The settings window opens on the settings record beside the settings the client keeps, which `game.ts` builds. A window closes with the player's choices as plain data, and imports no simulation module. A window showing holds the keyboard and mouse; no window holds the city. The year-end budget never waits for the player (see `Budget.doBudgetNow`): with auto-budget off, or when auto-budget couldn't cover the services, the budget window opens as a review once no other window shows, and the player's changes there are a `setBudget` command. `windowCommands.ts` turns the windows' choices into commands. Milestones are good-news notifications, not windows. `news.ts` decides where a message the simulation sends goes: to the notification bar, and the place it happened to the monster TV when the message marks it as one the TV shows or follows; neutral news that arrives while a disaster is recent is not shown, nor is an explosion's report while a crash or another disaster is. `speedControl.ts` sends the speed the player sets with Pause, Play and Settings as `setSpeed` commands, and shows the pause button from the speed in the settings record, the only record of whether the game is paused. The auto-bulldoze setting is the player's preference (`autoBulldozePreference.ts`), kept under its own `localStorage` key and sent with each tool command, never saved with the city.
- **City source** — the client reaches the city only through a `CitySource` (`citySource.ts`): it sends commands and queries, and the source delivers the state messages the city sends back (`protocol.ts`, `protocol/README.md`). The page imports no simulation module, not even for a type, but the vocabulary the two share, which `test/clientImports.ts` enforces: `protocol.ts`, the messages themselves; `messages.ts`, the names of the news subjects and advisor conditions those messages carry; `tileValues.ts`, the tile ids, by which the client draws and animates tiles; and `tileFlags.ts`, the flag bits of a tile's raw value, which the client masks and reads. A module joins the vocabulary only with its reason written here. `cityState.ts` is the client's copy of the city, built from those messages alone: the map, from the full map the city sends when it starts and the tile changes after it, and the latest message of each other type since the city started. The simulation's side of a source in the browser is `cityHost.ts`: it owns the `Simulation`, the command queue, the session's command recorder, and the step driver, and steps the city itself at the speed it was set to, on a loop of its own that runs from the first city's start. While the city isn't stepping (paused, unseen or held) the loop waits, and the next command, the player seeing the city again or the runner's release wakes it. After each turn of its loop that applied commands or took steps, and each call of the end-to-end runner's driver that applies commands or takes steps, it sends one batch of state messages: the tiles that changed, found by diffing the map against its own copy; the sprites, the date, the population and the records that differ from those it sent last; the latest `status` and `demand` the simulation published since the last batch; and the events since then in the order they came (news, command results, budget reviews due, and each recomputed overlay layer once). The page tells the source whether the player can see the city, which isn't a command: in a hidden tab or under the screen-too-small overlay a source in the browser stops stepping, and the server, whose city other players share, never hears it. The page plays through the WebSocket source (`webSocketCitySource.ts`) when a server welcomes the player, on the city's socket the city client holds, and otherwise through the Worker source (`workerCitySource.ts`): the host runs in a Web Worker, off the page's thread, which `micropolis.ts` starts from `cityWorker.ts`. The worker serves the host (`cityWorkerHost.ts`) over the messages `cityWorkerMessages.ts` defines, starting with whether the page is in debug mode, and answers each call after the state messages it caused, so the page has the state before the call resolves. What goes wrong in the worker outside a call, a promise rejected with no one to catch it included, is raised in the page. `test/workerImports.ts` checks the worker's TypeScript modules against the Web Worker library, which has no `window` or `document`. `pageCitySource.ts` is the in-page source, which runs the host on the client's own thread, for the contract tests. The tests of client code that need a city or a query's answer run against a fake source (`test/helpers/fakeCitySource.ts`), which plays back the state messages and query answers recorded from the server, in `test/recordings/`. A recording is an opening, the calls every branch starts with, and its branches, one for each way a test goes on from there, each recorded on a city of its own; tests that make the same calls share a branch. The calls a test makes must be the recording's, in its order, or the fake fails naming the call it expected, and a test that stops short of its branch fails through `expectPlayedThrough`, which each suite calls itself. A new case is a branch added to `test/recordings/scenarios.ts`, then `npm run record` (`test/recordings/record.ts`), after `dotnet build server/Micropolis.slnx`: it records every scenario again from the server's Debug build, naming the ids the server makes up so a recording made again is the same file. The recordings are never edited by hand. The three sources pass the same contract tests (`test/citySource.ts`), the WebSocket source against the real server, except where a city on the server differs by design: it steps whether or not a player sees it, has no client debug mode, and its failures come back in the C# rules' words. The bundle is built from ES modules, which `new Worker(new URL(..., import.meta.url))` needs, by an override of ts-loader's module settings in `webpack.config.js`; `tsconfig.json` stays on CommonJS for ts-jest. `stepDriver.ts` turns real time into steps at a fixed 60 per second. It catches up after a slow frame, up to a second's worth of steps at a time, and drops the rest of a longer gap. It owes nothing while the city is not stepping: paused, while the player can't see it, or while the end-to-end runner holds it. Map previews are a `mapPreview` query, which a source answers before any city has started; a save's text goes to a source in the browser and back unread by the page, which only stores it (`storage.ts`); a city on the server is saved to the server's store, and its source gives the page no text.
- **Headless** — `headless/` runs the simulation in Node through `tsx`, without a browser: `runner.ts` starts a city from a seed or a fixture and steps it, failing rather than stalling silently (`cityTimeModel.ts` takes the steps and checks city time kept up, for it and for a city the end-to-end test hook drives in the browser alike), and replays command logs; `run.ts` is its command line, which `cli.ts` prints. A fixture is a command log in `headless/fixtures/`, whose checkpoints are its golden hashes. Its script either lays out its tool commands, or takes the city another fixture's commands build, writes onto it what no command places, and starts the log from that city's save. Each fixture and mid-run log has its entry in `server/Micropolis.Headless/Fixtures.cs` too, from which the C# fixture tool writes the same log, so a new one is added on both sides, or the tool's tests fail. The runner and the TypeScript tests build a fixture by replaying its commands each time they use it, then load its saved state. The copies of its state in `conformance/saves/`, and of its log in `conformance/logs/`, are for the C# tests, the saves for the benchmark too, and the logs for the C# headless runner, which starts a fixture that writes onto a city from the save in its log. The state hash (`stateHash.ts`, specified in `docs/state-hash.md`) is SHA-256 over the canonical text of the saved state.
- **Rendering** — `gameCanvas.ts` draws the map with WebGL2 (`webglRenderer.ts`). On each animation frame it draws the part of the view whose picture would differ from the last one drawn (`FrameRecord` in `mapDamage.ts`): all of it when the view moved, zoomed or was resized, the overlay changed, a lost WebGL context was restored, or more than half the view's blocks changed, and otherwise the square blocks of tiles that changed, as far as a changed tile's shadow reaches, and where a sprite that changed was and is, each rounded out to whole device pixels, over the drawing buffer it keeps. It draws nothing while the GPU is still drawing the frame before, so on software WebGL on a busy machine frames never queue behind each other and hold up the page; the end-to-end runner waits for the map to be drawn to the end before it reads the screen. It draws in three passes over the tiles in view, and for the shadows over a margin around them as wide as the farthest shadow reaches: every tile's ground; every shadow, merged by the darkest value into a shadow buffer with `blendEquation(MAX)`, which then darkens the ground once; every tile's objects; then the overlay's tint and the sprites. `mapFrame.ts` builds each pass's quads, as pure functions tested under Node. The art comes from a manifest and atlases in `images/render/`, which `docs/render-assets.md` specifies and `renderManifest.ts` reads: a tile id or sprite frame the manifest leaves out is drawn from the 16 px sheets, `images/tiles.png` and `images/sprites.png`, nearest-neighbour, while rendered art is mipmapped. A browser without WebGL2 gets a message instead of the game. The tools' outlines (`mouseBox.ts`) are drawn on a 2D canvas over the map, which the pointer's events pass through. The view zooms through fixed steps of CSS pixels a tile (`ZOOM_STEPS` in `viewPosition.ts`), with the mouse wheel and the + and - keys, around the pointer, or the middle of the view when the pointer is off the map, with its origin on whole tiles, but not in the middle of a drag; it opens at the first step, the 16 px of the fallback art, and the zoom is a client view setting, never city state. The backing stores of the map's canvas and of the outlines' canvas over it have `devicePixelRatio` pixels to the CSS pixel, while pointer positions, the tile width and the test hook's view are CSS pixels. `animationManager.ts` animates tiles from their value and the client's clock, and never writes the map: an explosion holds its last frame until the simulation's scan turns the tile to rubble. `monsterTV.ts` is the small disaster-follow view, which follows a monster or tornado by its type through the sprites messages, and draws from the 16 px sheets with Canvas 2D (`tileCanvas.ts`, through `tileSet.ts`), as `splashCanvas.ts` draws the map preview on the splash screen. A map overlay tints each tile, under the sprites: `overlayRenderer.ts` works out one layer's colour ramp and legend from the simulation's answer to an overlay query alone, never from simulation objects; `overlayPicker.ts` asks for the layer the player picks, and again each time the simulation announces it recomputed.
- **Server** — `server/` is a .NET 10 solution, `Micropolis.slnx`, with a test project per project. `Micropolis.Rules` holds the game rules and the server's half of the protocol, and has no ASP.NET dependency, so a test or a tool can run them without a host. `Micropolis.Benchmarks` is such a tool, a console app: for each fixture's save in `conformance/saves/`, and a new city at each running speed, it times the simulation's steps and writes a Markdown table of steps per second and time per step, with the machine, its load average, the runtime and the commit. Beside them it tables the state-message bytes per step a player in the city is sent, taking one step a turn of the server's loop, as it does on average: the batch the server builds after the turn (`CityStateMessages`), counted as the UTF-8 bytes of the text the server sends it in, after checking that the city they were measured on ends at the state hash its timed city does. `npm run benchmark` runs it in Release and has it write `docs/benchmarks.md`. `Micropolis.Headless` is another, the C# headless runner and fixture tool: it takes the TypeScript runner's options and prints what it prints, but for arguments it can't run, which it answers with the usage too and exit code 2, where the TypeScript runner prints only the problem and exits with 1. It replays a log through `CommandLog` and `LogReplay` in `Micropolis.Rules`, and fails rather than stalling silently (`CityTimeModel` takes the steps and checks city time kept up). With `--write-fixtures` it writes every log under `conformance/logs/`: each fixture's and mid-run log from its commands as `Fixtures.cs` lays them out, with the checkpoints its replay in C# reaches, and the playthrough's copied from `e2e/goldenPlaythrough.json`, once its replay matches every checkpoint. A fixture that writes onto a city what no command places starts from the save its log keeps, which is committed data: the TypeScript script wrote it, and the tool writes it back unchanged. While the TypeScript simulation exists, `npm run conformance` writes the logs and the tool must write them the same: its tests fail unless every log it writes is the committed file byte for byte. `Micropolis.SourceTree` reads files of the repository in place, from the root its build recorded, for the tests and tools that read the files the repository shares between its sides; the server never references it, so no build path ships with the game. `Micropolis.Server` is the ASP.NET Core host. `POST /api/session` signs a player in with a display name only, a few times a minute per client address: the token's subject is a new player id, the name is the only claim the server adds, and it carries no roles, because no player can be denied anything. `GET /api/session` answers who a token belongs to, or 401, which is also how the browser finds out that a server answers. `/ws/city` is one plain WebSocket of JSON messages, where `PlayerPresence` lists who is online and each `CityConnection` is the one writer to its socket. The server closes a connection when its token expires. The server owns the cities (Direction 2). A player starts a city, which gets an id, uploads a saved game, which starts a copy of it under a new id (the game does this when a player loads a save while online), or joins one by its id, and `CitySession` handles a connection's messages in the order they came, in one city at a time. `CityLimits` bounds how many cities one client address starts in ten minutes, how fast it sends commands, past which the server closes its connection, and how often it saves, past which the save fails and the connection stays. `CityRegistry` keeps each city loaded while a player is in it, as a `LoadedCity`, and in `CityStore` while none is: it saves a city as it starts, as a player saves it with the Save button, as its last player leaves, which unloads it, and as the server stops, and a join loads it again. The city's work only takes a save, and the store keeps one city's saves in the order they were taken, off that work (`LoadedCity.SaveAsync`), so an older save never lands over a newer one, an unload's included. A save the store can't keep fails, and leaves the city loaded, so the next save keeps it. Online, the Save button keeps the city in the store and nowhere else: the page's storage keeps only a city played in the browser (`citySave.ts`), and the end-to-end runner reads a city's save through the debug channel, which keeps it nowhere. `CityStore` keeps each city as a row of a SQLite database, read and written through EasyReasy.Database with its `.Sqlite` and `.Mapping` packages: the city's id, its saved game, when it was last saved, and when it was last opened (started, or loaded for a player entering it); nothing deletes a city. `CityDatabase` brings the database up to date as the server starts, before the host builds, with DbUp running the numbered SQL scripts in `Micropolis.Server/Migrations/`, embedded in the assembly; a change to the schema is a new script after the last, never an edit to one that has run. The store's tests (`CityStoreTests`) share one migrated database through EasyReasy.Database.Testing, each working in a transaction it never commits. Every other database a test uses is a fresh file of its own, migrated the same way: one whose store outlives a store or has writers of its own, the registry's, each in-process test server's (`ServerUnderTest`), and each server's the client's tests start (`test/helpers/testServer.ts`). A loaded city's work runs one piece at a time, in the order given: its loop's turns, every player's commands in the order the server received them, and the requests. `CityHost` is `cityHost.ts` ported: the step driver at 60 steps a second (`StepDriver`), the city's one command queue and log, with checkpoints the C# state hash computes (`CommandQueue`, `CommandRecorder`, which records the log as the `CommandLog` of `Micropolis.Rules` that the fixture tool writes and `LogReplay` replays), and the state messages found by diffing (`HostedCity`, on `CityStateMessages` in `Micropolis.Rules`), which every player in the city is sent alike; a player who joins is sent the whole city first. A player's hover box goes no further than the city's other players: `CitySession` drops one that no tool makes on the city's map (`CursorBounds` in `Micropolis.Rules`, on the tool sizes in `CityTools`) or past 20 in any second from one connection (`CursorLimit`), and `LoadedCity` passes the rest on, one box per player, so when one connection's box stops showing the others see the box another of the player's connections shows, or null. A city whose work throws is unloaded without saving, so it stays as it was last saved, and its players' connections are closed with 1011; the page then says the city was lost and goes to its address without the city's link (`cityLink.ts`), where the player chooses a city. A city the WebSocket source can't join again after a reconnect is lost the same way. The debug channel (hold, release, flush, advance, city time, the saved game's text, and the turn of a manual clock) answers only in a Debug build (`DebugChannel`).
- **Server connection (client)** — `cityClient.ts` signs in and holds the city's WebSocket, with no DOM, so its tests drive it through a fake browser; `browserCityEnvironment.ts` gives it the browser's fetch, WebSocket, storage and locks. With no server answering, the game starts single-player. Once online, it reconnects after a drop with growing delays, and signs in again under the stored name when the server rejects its token, one tab at a time, so tabs sharing a session stay one player. `signInForm.ts` asks for a name before the splash screen when a server answers and no session is stored, or the server refuses the stored name, and `onlineList.ts` shows who is online, or "Offline", over the top of the map. The client hands the city's messages on the socket to the WebSocket source, which joins its city again after a reconnect; a request made while the connection is down fails, and a command sent then is lost, with a warning, as is a query, which is never answered, and so is one still waiting when the connection drops. Under the online list, the activity list (`activityList.ts`, deciding in `playerActivity.ts`) names what the other players did, from each command result's player and the names the server lists, and never the player's own commands or a failed one, which only its sender learns of in the tool output: a fading line per player per thing done, so a drag's commands make one line, apart from the notification bar, so a player's activity never pushes city news off it. With no server it lists nothing. The players' hover boxes travel as `cursor` messages, which the server passes on to the city's other players and never to the simulation or a log: `playerCursors.ts` decides when this player's box goes and which of the others' the map shows, each in the colour of the tool its player holds, as this player's own is, with their name beside it on a tag in a colour their id picks. Both the list and the boxes know who is who from one `PlayerRoster` (`playerRoster.ts`), and `OtherPlayers` (`otherPlayers.ts`) holds the three for the game.
- **Protocol** — `src/protocol.ts` and `server/Micropolis.Rules/Protocol.cs` define the bodies of `/api/session`, the WebSocket's messages and the commands by hand, the messages a player sends in `ClientMessages.cs`. `src/protocol.ts` also defines the queries with their answers, the records the simulation produces for the windows to show, and the state messages, which the server mirrors in `QueryAnswers.cs` and `StateMessages.cs`. `protocol/README.md` specifies the wire format, and the examples and reader cases under `protocol/` pin the sides together: each test suite reads in place the examples of what its side reads or writes. A change to a state message or a query answer also moves the client's test streams (`test/recordings/`), which the same commit records again (`npm run record`).
- **Conformance data** — `conformance/` holds what the C# implementation of the game rules tests against, and what computes it: the random stream's vectors, from a C reference that the TypeScript tests read too, and files the TypeScript reference writes, among them a copy of the end-to-end playthrough's log. The C# tests read them in place. `conformance/README.md` describes each file.

### The simulation cycle

`Simulation.step()` is one loop, as `simLoop` in the original: `_simFrame()` gates on the game speed, then every sprite moves. The gate is the saved `_speedCycle` counter, which lets a phase through on every 5th step at slow speed, every 3rd at medium and every step at fast. A paused simulation's step does nothing. The step count, never wall time, advances the city. Each step that passes the gate runs `simulate()`, which advances one phase of a 16-phase cycle:

| Phase | Work |
|-------|------|
| 0     | advance `_cityTime` and `_simCycle`, set the demand valves, clear the census |
| 1–8   | scan one eighth of the map's columns each, calling the tile handlers |
| 9     | census, tax collection and city evaluation at their frequencies |
| 10    | decay the rate-of-growth and traffic maps, send advisor messages |
| 11–15 | power scan; pollution, terrain and land value; crime; population density; fire coverage and disasters, then publish the city status record |

How often phases 11–15 run depends on the game speed (`speedPowerScan` and its siblings in `simulation.js`), so speed changes simulation results. It is simulation state, not a display setting.

### Tile handlers

Subsystems register handlers with `mapScanner.addAction(tileValueOrPredicate, handler)` from `registerHandlers`, all called in `Simulation.init`. During phases 1–8 the scanner calls the handler for every matching tile with `(map, x, y, simData)`; `simData` (from `_constructSimData`) carries the census, budget, block maps, the random stream, the sprite manager and the other managers.

### State

- `gameMap.js` holds the tile grid. `tile.ts` is a tile's value plus flags (`tileFlags.ts`: powered, conductive, burnable, bulldozable, zone centre…). `tileValues.ts` names every tile id (`RIVER`, `CHANNEL`, `PORT`…).
- `simulation.blockMaps` holds coarse overlays at block sizes 2, 4 or 8 (`blockMap.ts`): land value, pollution, crime, traffic density, population density, police and fire coverage, rate of growth. Each map's comment in the `Simulation` constructor states its range.
- `simulation.random` is the simulation's random stream (`random.ts`), seeded from the game seed. The map generator draws from the same seed's map stream, so one seed reproduces map and city. The `random.ts` header specifies the stream, which the C# port (`RandomStream` in `server/Micropolis.Rules`) reproduces bit for bit. `conformance/random.json` holds reference vectors computed by the reference C implementation, and the tests of both read it in place.
- A stateful component's `save(saveData)` and `load(saveData)` write and read its fields under its own key of the save. What the scans derive is saved under `scannedState` instead, through `saveScan` and `loadScan`: the census has both pairs, and the power manager, which holds only scan results, has only the scan pair. `test/savedFields.ts` fails on a field a component holds but neither saves nor explains. A save holds the complete simulation state, the stream's included, so a loaded city continues exactly as it would have without the save; `docs/state-hash.md` lists every key, and a field the simulation adds is saved and listed there too. The `Simulation` constructor starts a new city from a seed, and `Simulation.fromSave` builds one from a save. `Simulation.load` restores a save over a city of the same map size, and nothing of the city it replaces survives. It restores without scanning, except for a browser save that `transitionOldSave` migrated from a version without the scanned state: that save's scanned state is `null`, so loading derives it by scanning from a new city's scanned state, then restores the rest of the save over whatever the scan changed. `savedGame.ts` writes the combined object, versions it (`SaveFormat.CURRENT_VERSION`) and migrates old saves (`transitionOldSave`), on the simulation's side of the city source; `storage.ts` keeps the text in the page. On the server, `SavedGame.Write` in `server/Micropolis.Rules` writes the same text, which `CityStore` keeps. The version is one past the last of the migration steps in `UPGRADES`, each of which upgrades a save from its place in the list, so a step only ever goes at the end. A change to saved state appends a migration step, which bumps the version, updates the golden hashes, regenerates the conformance files (`npm run conformance`), changes the C# save model in `server/Micropolis.Rules` to read it, and records the client's test streams again (`npm run record`) where what the server sends moved, in the same commit. The same commit appends the same step to `Upgrades` in `SavedGame.cs`, which migrates saves in C#, and adds a sample save of the new version, written by the game of that commit, to `conformance/saveVersions/`.

### Events

`eventEmitter.js` decorates a simulation constructor or object with `addEventListener`, `removeEventListener` and `_emitEvent`. Event names live in `messages.ts`, each a string no other message shares, since listeners and the unit snapshots tell events apart by the string; `test/messages.ts` fails on two that share one, and `MessagesTests` on two C# names that do. Subsystems emit, `Simulation` re-emits upward, and the city host turns what it hears into state messages for the client: the simulation never calls UI code. The client's windows and input announce what the player does through their own base, `Emitter` in `emitter.ts`.

A condition that holds over time (power load against capacity, a demand cap, an advisor warning) is state, published each cycle in the `CITY_STATUS_UPDATED` record, which reaches the client as a `status` message that `statusPanel.ts` renders. A `FRONT_END_MESSAGE` notification announces a condition or a one-off event and then times out; the record is what shows a condition for as long as it holds. The record is built each cycle and not saved, but its sources are: the power figures from the last power scan, and the cap flags from the valves.

### Sprites

`spriteManager.js` and the `*Sprite.js` files: train, ship, plane, helicopter, monster, tornado and explosion. Sprites move once per simulation step (`Simulation.step` → `spriteManager.moveObjects`), at the same rate whatever the game speed, and draw from the simulation's stream, so their behaviour, including the map damage a crash, monster or tornado causes, is part of the deterministic simulation.

### Commands

Every change a player makes to the city is a command: plain JSON, defined in `protocol.ts` as part of the multiplayer protocol. UI code never writes to the map, the budget or the managers. `Simulation.applyCommands` validates each command (`commandRejection`) and applies it, separately from `step()`. A rejected command changes nothing. Each command's result, with the player who sent it, its outcome and the reason for a rejection, is emitted as `COMMAND_RESULT`; the simulation never branches on the player. `commandQueue.ts` drives a simulation as the city host does, and `CommandQueue` in `server/Micropolis.Server` as the server does: commands queue as they arrive and apply in arrival order whenever `applyCommands` is called, every turn of the host's loop whether or not the city is stepping, and each is stamped with the index of the step it precedes. The queue hands each stamped command, and each step before it is taken, to a recorder: `commandLog.ts` records the session's command log (`docs/command-log.md`), with a checkpoint of the state hash every 3,600 steps, which the debug window downloads and the headless runner replays. The UI turns clicks and drags into tile paths: `dragPath.ts` gathers the tiles the tool reaches, filling in those a fast mouse skips, and each tick sends a drag's new tiles as one tool command.

A query asks the simulation about the city and changes nothing: plain JSON, defined in `protocol.ts` beside the commands. `Simulation.answerQuery` validates it (`queryRejection` in `queries.ts`) and answers at once, with a copy of what it reads; it never draws from the stream and is never logged. An `overlay` query names a layer, one of the block maps the player can see or the power grid, and is answered with the layer's block size, range and values. The simulation emits `OVERLAY_UPDATED` with a layer's name once the phase that recomputes it has run (`LAYER_PHASES`), which reaches the client as an `overlayUpdated` message, and an overlay showing that layer asks again. A `tileReport` query names a tile, and is answered with the tile's raw values and its category, the table of the original's `doZoneStatus`; the client sorts the values into the bands the query window shows. A `budgetForecast` query names the funding of some services, and is answered with the budget record and what the year end would cost and leave at that funding, as `Budget.forecast` works it out. A `mapPreview` query names a game seed, and is answered with the map a new city on it starts on, before any city has started too.

### Tools

`*Tool.js` on top of `baseTool.js`; `cityTools.ts` builds the tools that change the city, with their costs, which the simulation applies tool commands with. A tool command applies its tool at each tile of its path in order, as one click each: the tool stages its edits in a `WorldEffects` (`worldEffects.js`), drawing from the stream as it goes, checks the funds, then writes the staged tiles to the map and charges the budget. The query tool (`queryTool.ts`) belongs to the UI: it sends a `tileReport` query for the tile clicked, and the query window shows the answer. It asks, as the overlay picker does, through a `QuerySource` (`querySource.ts`), which the city source is.

## Rules for simulation code

- **Deterministic.** Randomness comes only from `random.ts`; time comes only from counters the simulation advances as it steps. A `Math.random`, `Date` or `performance.now` read inside simulation code is a defect to fix, not a pattern to copy. Only what changes city state draws from the simulation's stream, tools and disasters included; the UI's own randomness, such as picking a new seed, comes from `uiRandom.ts`.
- **No DOM.** No `window` or `document` in simulation modules.
- **Simulation modules** are every file the simulation (`simulation.js`), the map generator (`mapGenerator.js`) or a map-editing tool (`cityTools.ts`, and every `*Tool.js`) imports, directly or not. `test/simulationImports.ts` walks that graph with the TypeScript checker and fails on any global but a short list of pure built-ins, on any `Math` function outside the portable ones, and on `**`, a package import or a dynamic import. `PortableRulesTests` holds the compiled `Micropolis.Rules` to the same rules through its metadata: no clock, `Random` or `HashCode`, nothing of `Environment` but the thread id the compiler's iterators read, and no `Math` function outside the portable ones, nor a generic math interface that offers the others. Beside them, `SavedFieldsTests` fails on a field a C# component holds but neither saves nor explains, as `test/savedFields.ts` does, and `DeterminismTests` on two runs from one start that differ.
- **Portable arithmetic.** No transcendental `Math` functions (`sqrt`, `pow`, `sin`, `log`…) in simulation code: their results can differ between runtimes. Arithmetic is fine, and so are the `Math` functions whose results are exact everywhere, which `PORTABLE_MATH` in `test/simulationImports.ts` lists. The C# port mirrors each: `Math.trunc` copies C's conversion to a whole number, which drops the fraction toward zero, as a C# `(int)` or `(long)` cast does, and JavaScript's `Math.round` sends halves toward +∞ rather than to even. `Math.fround` rounds to the nearest IEEE single, as a C# `(float)` cast does. It reproduces the original's float arithmetic where a rule depends on it, provided every float operand and the result of each single `+`, `-`, `*` or `/` is wrapped in it: `Math.fround(Math.fround(a) * Math.fround(b))` is the float product, but `Math.fround(a * b + c)` is not the float sum of a float product.
- **Rule changes are deliberate.** The original's numbers are tuned against each other. A change to how the city behaves is named as such in its commit, never folded into a refactor. Each fixture's log pins its state hash as built and after a fixed run, as checkpoints that `test/goldenHashes.ts` replays. A change to a fixture's commands, to saved state or to a rule moves them, and that commit updates them and regenerates the conformance files (`npm run conformance`), whose logs the C# tool must then write the same (`--write-fixtures`). A change to a rule or to saved state moves the client's test streams too, which the server's C# rules produce, so the same commit records them again (`npm run record`). A refactor that moves one is a defect. A run hash that moves while the built hash holds is a change to how the city behaves. The playthrough's golden checkpoints and log (`e2e/goldenPlaythrough.json`, rewritten by `npm run e2e:golden`) move for the same reasons, and for a change to a stage, to the commands or to how the game turns input into them; the commit that rewrites them says why, and then regenerates the conformance files, whose generator copies the log to `conformance/logs/playthrough.log.json` and fails while the golden log no longer replays, so `npm run e2e:golden` runs first.

## The original as reference

The original C/C++ source is the behavioural reference: <https://github.com/SimHacker/micropolis>, engine in `MicropolisCore/src/MicropolisEngine/src/`. The behaviour of the original's windows, such as the budget window's sliders, lives in the older C and Tcl version under `micropolis-activity/src/sim/` (`w_budget.c`, `w_sim.c`) and its Tcl scripts. This port follows it closely, function by function — for example `boatSprite.js` mirrors `doShipSprite` in `sprite.cpp`. When something behaves oddly, compare against the original before calling it a port bug: much odd behaviour is faithful to 1989, such as ships that wander the channel at random and wreck at dead ends.

Where the original's behaviour is undefined in C, the port keeps defined, portable behaviour and names the divergence in a comment at the code. Implementation-defined integer narrowing is matched.

## Code style

- Client modules are TypeScript, and so is every new module. Legacy simulation modules stay JavaScript, since the C# port retires them.
- The client works on the DOM directly, through the helpers in `domElements.ts`. `test/noJquery.ts` fails on any module under `src/` that imports jQuery.
- JavaScript modules name the file extension in their imports (`./tile.ts`, `./budget.js`); webpack's `extensionAlias` resolves both. TypeScript modules import TypeScript files without an extension (`./tile`), because `tsconfig.json` rejects a `.ts` suffix, and name it for JavaScript files (`./simulation.js`).
- `tsconfig.json` is strict, including `noUnusedLocals` and `noUnusedParameters`.
- Every source file keeps the GPL and Micropolis header comment at the top, new files included, C# and C as well.
- C#: block-scoped namespaces, explicit types rather than `var`, and nullable reference types; `server/Directory.Build.props` treats warnings as errors. Tests are MSTest, named `Method_Scenario_Expectation`.

## Hard Rules — Stop and Ask

If any of these arise, **stop immediately** and ask for guidance before continuing:

1. **Architectural dead-end**: the implementation cannot be solved cleanly. Explain the constraint and suggest clean alternatives.
2. **Hacky path**: mid-implementation you realise the approach involves workarounds or quality compromises. Discard it and propose the clean path. No sunk cost fallacy, no "just make it work for now".
3. **Against the direction**: the right implementation contradicts the Direction section or settles an Open decision. Raise it first; don't drift silently.
